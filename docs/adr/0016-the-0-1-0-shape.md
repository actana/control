# The 0.1.0 shape: two images, one installer, three workflows

This ADR is the handoff spec for the rebuild charted on [#6](https://github.com/actana/control/issues/6). Eleven tickets (#7–#17) produced decisions rather than code; this records them as one locked set so an implementation effort can start with nothing left to argue about. It is longer than every other ADR here, deliberately: the alternative was a `SPEC.md`, and this repo is deleting one of those for being unreviewable and self-superseding. An ADR is permanent, diffable, and amended by PR — which is the property that matters once `main` is protected.

**How to read it.** Each clause states what is locked and the measurement that locked it, then links to the ticket comment that argued it. The evidence stays on the tracker; it is not restated here. A clause is changed by amending this file in a PR, never by a comment on an issue. Where a clause overturns something in #6's own frame, it says so.

**Scanner provenance for every CVE number below:** Trivy 0.73.0, vulnerability DB `2026-08-03T07:52:05Z`, `--scanners vuln --pkg-types os,library`, counted on a **distinct-CVE** basis. Numbers from a different scanner or a different day are not comparable and should not be quoted against these ([#7](https://github.com/actana/control/issues/7)).

## A. Vocabulary and packages

**D1 — One vocabulary, and "Agent" is retired.** A **Panel** controls many **Cores**; a Core runs many **sessions**; each session drives one **Harness** (`claude-code`, `codex`, `cursor-cli`, `opencode`). "Harness" survives in exactly one sense — the CLI — and the machine sense dies. "Agent" is not domain vocabulary in either sense. ([#12 §1](https://github.com/actana/control/issues/12))

**D2 — The rename is two renames and lands as one sweep.** Machine `Harness` → `Core`; `TaskAgent`/`AiRuntimeHarness` → `Harness`. 233 live files. Splitting the sweep leaves a window where the repo says Core, Agent *and* Harness for two concepts — strictly worse than today, so it is one PR. Release assets become `actana-core-<version>-<target>.tar.gz`; the systemd unit becomes `actana-core.service`. Exception: macOS **LaunchAgent** is an OS term and stays (and dies with the macOS targets anyway). ([#12 §1, §3](https://github.com/actana/control/issues/12))

**D3 — `packages/shared` survives as a third package.** It holds the Panel↔Core wire contract (`core-link-frames.ts`, `registration-blob.ts`). Folding it into either side would make one image depend on the other and break the two-image split. While renaming, fix the asymmetry: Core imports it by relative path in 45 places and esbuild inlines it, so the declared `@actana/shared` dependency is never imported by name — point Core at the package name so the boundary is real. **Closes #6's open item "fate of `packages/shared`."** ([#12 §5](https://github.com/actana/control/issues/12))

**D4 — What does *not* move.** The CLI binary stays `actana`. The `AC_` and `ACTANA_` prefixes stay; only the eight `AC_HARNESS_*` variables move to `AC_CORE_*`, with `AC_HARNESS_CORE_ID` → `AC_CORE_ID` and `AC_HARNESS_LISTENING`/`AC_LISTENING` collapsing to one `AC_CORE_LISTENING`. `BUNDLED_NODE_VERSION` is already neutral. Install paths are already brand-named. The Panel's schema is already Core-named — tables are `cores` and `core_secrets` — so there is **zero persisted-data impact on either side**. ([#12 §3, §6](https://github.com/actana/control/issues/12))

## B. The Core image

**D5 — Base is `ubuntu:24.04`, digest-pinned, with `apt-get upgrade -y` in the same `RUN` layer.** Both halves are load-bearing and do different jobs: `24.04` is a *rolling* tag that moves on every point release, so only a digest is a pin; and apt resolves `noble-security` at build time, so a weekly rebuild on an unchanged digest still collects every fix Canonical has shipped. Without the upgrade the pin freezes the CVEs too and the rebuild cadence is theatre. This is deliberately against Docker's stock advice, because here drifting toward `noble-security` is the point and the digest bounds the drift. Alpine and `node:24-alpine` were eliminated on the musl gate — the bundled glibc Node exits 127 for a missing ELF interpreter. Wolfi is the strongest rejected candidate and is rejected on reproducibility, not on capability: its free anonymous tier publishes only a mutable `latest` with no digest-retention guarantee, so its 0 and reproducibility are mutually exclusive. ([#7](https://github.com/actana/control/issues/7), [#8 §1](https://github.com/actana/control/issues/8))

**D6 — The package set, and it is where the CVE number actually moves.** In: `bash sudo ca-certificates curl git openssh-client build-essential python3 ripgrep jq less vim-tiny unzip lsof xz-utils tini`. Out: `zip`, `wget`, `gnupg`, and every systemd package. `lsof` is new — without it `pty-manager.ts`'s port-conflict probe is silently a no-op, which it is in today's dev Core. **`1248 → ~38 distinct CVEs, 751 → ~190 MB.**

> Anyone summarising this must say it correctly: the base did change, but the *mechanism* that moves the number is the package set. `build-essential` → `libc6-dev` → `linux-libc-dev` accounts for **1200 of 1328 OS findings**, and dropping that one package alone takes an unchanged `ubuntu:24.04` build from 1248 to 38. Claiming the base did the work is false and will mislead the next person who reads it.

**Amended 2026-08-04 by [#37](https://github.com/actana/control/issues/37), which built the clause and scanned it.** The mechanism is confirmed exactly — `linux-libc-dev` is 1200 findings, and the base contributes 6 — so the paragraph above stands as written. **`751 → ~190 MB` does not, and is withdrawn.** The built image is **805 MB**. ~190 MB is the package set *without* `build-essential` and `python3` (measured: 203 MB), and D7 keeps them on purpose; they are +272 MB, and Node plus the Core tarball a further +330 MB. "Toolchain in" and "~190 MB" were never simultaneously achievable, and the size half of this clause should not be quoted. The CVE half survives: 46 distinct after D7's suppression against the ~38 predicted, the difference being Node/npm rows the D6 baseline did not carry. (Scanned on the next day's DB, so per the provenance note above the counts are indicative rather than a like-for-like comparison; the size figures are not scanner-dependent at all.) Evidence: [`docs/research/core-base-measure/core-image-2026-08-04.md`](../research/core-base-measure/core-image-2026-08-04.md).

([#7](https://github.com/actana/control/issues/7), [#8 §2](https://github.com/actana/control/issues/8))

**D7 — The native-addon toolchain ships, and its 1200 findings are suppressed with the justification checked in.** `build-essential` and `python3` stay because a Core exists to run Harnesses against real repos: `npm install` on any project with a native addon invokes node-gyp, which needs `make`, `g++` **and** `python3`. This repo is the proof — it depends on `better-sqlite3` and `node-pty`, so a Core without the toolchain cannot `pnpm install` Actana Control itself, and the failure mode is a wall of node-gyp output rather than "install build-essential". The spec calls this suppression rather than laundering it:

> The Core ships a native-addon toolchain because that is what the product is. Its ~1200 findings are `linux-libc-dev` kernel headers — 1008 of its 1015 files are under `/usr/include`, there is no executable code, and the kernel a Core runs is the host's. They are suppressed by **a single entry in a checked-in `.trivyignore` with that justification written beside it, and nothing else is suppressed anywhere.**

**Amended 2026-08-04 by [#38](https://github.com/actana/control/issues/38): "nothing else is suppressed anywhere" is no longer true, and D11's amendment says why.** The allowlist file is still one file with one entry — that half stands, and the file is `.trivyignore.rego` for the reason recorded under D11. But the gate also scopes out the system Node's own bundled npm tree by path, and that is a second suppression. It is not in the allowlist file, so D7's "one entry" survives literally; read this clause as governing **the allowlist**, not as a claim that the gate suppresses nothing else. The full count is two, both written down, and neither may grow without amending this ADR.

([#8 §2](https://github.com/actana/control/issues/8))

**D8 — Node 24 arrives as the nodejs.org tarball, sha256-verified.** `ARG NODE_VERSION=24.18.1`, checked against that release's own `SHASUMS256.txt` — the pattern `scripts/lib/core-tarball.mjs` already implements. No NodeSource, no third-party apt repo, no unverified download. There is effectively no alternative (no stable Debian or Ubuntu archive carries Node 24, and no `-backports` suite carries `nodejs` at all) and the two UBI rows prove the delivery method does not move risk — tarball 143 distinct vs RPM 144. This system Node exists **only** for `npm i -g @openai/codex` and Harness-run npm work; the daemon execs the Node bundled in its own tarball. A comment in the Dockerfile must warn against "simplifying" this to `apt-get install nodejs`, which would get Node 18 *and* move it onto Ubuntu's Pro-gated *universe* security stream in one move. ([#7](https://github.com/actana/control/issues/7), [#8 §4](https://github.com/actana/control/issues/8))

**Amended 2026-08-04 by [#44](https://github.com/actana/control/issues/44), which gave the pin an owner.** The clause stands; one thing in it is no longer a value to keep current here.

> `24.18.1` is the version at the time of writing and nothing more. The pin is now bumped weekly by the `base-pins` job in [`.github/workflows/housekeeping.yml`](../../.github/workflows/housekeeping.yml), which reads nodejs.org's release index and opens the PR, because it is a tarball rather than an image reference and Dependabot's `docker` ecosystem cannot see it (D10's third mechanism). **A `NODE_VERSION` bump does not need to amend this clause** — the decision here is the delivery method and the sha256 verification, not the patch release. What that bump buys is Node's own security fixes; it does *not* clear the image's fixable CRITICAL/HIGH, per D10's and D11's amendments.

**D9 — Harnesses are not baked into the image. This overturns #6 frame item 2.** They are ~1.15 GB of what would be a ~1.4 GB image, add ~1 finding, ship on their own cadences and are stale within days of a build, and baking them means redistributing four vendors' binaries under licences nobody has cleared. They install at runtime via `actana setup --with-<id>` or `actana harnesses install <id>` into `$HOME`, which is the persistent volume — so they survive every image upgrade and self-update in place, which baked binaries would not. **Frame item 2 is now false as written and must not be cited as settled.** Two lines of #9 were written on the baked assumption (its glossary delta for "Core image", and its §6 safe-to-lose list) and are corrected by this clause. ([#8 §3](https://github.com/actana/control/issues/8), [C5](https://github.com/actana/control/issues/6))

**D10 — Three rebuild mechanisms, because they catch different drift.** Weekly (Monday) rebuild-and-republish in `housekeeping`, which is what pays down the fixable findings via D5's in-layer upgrade; Dependabot on the base digest, landing as a normal reviewed PR; and `NODE_VERSION` bumps on each Node 24.x release, which is the only thing that clears the Node-attributed findings including the single CRITICAL and all four HIGH. Weekly rather than nightly: Canonical does not ship security updates nightly. ([#8 §5](https://github.com/actana/control/issues/8))

**Amended 2026-08-04 by [#37](https://github.com/actana/control/issues/37).** Two of the three mechanisms are measured weaker than this clause claims, and [#51](https://github.com/actana/control/issues/51) and [#38](https://github.com/actana/control/issues/38) must be written on the corrected version.

> On the pinned digest, D5's in-layer upgrade currently pays down **nothing**: `apt-get -s upgrade` reports `0 upgraded`, and the scan is identical either side of it. The 21 distinct / 15 fixable #7 measured on the *rolling* tag had already been absorbed into `noble-20260730.1` by the time the digest was chosen — which is D5's own point restated, not a contradiction of it. Keep the layer: with the digest now frozen it is the only route a future Canonical fix can take. But it is prepaid insurance, and the weekly rebuild's justification cannot be a 21→6 drop it is not producing.
>
> "`NODE_VERSION` bumps … the only thing that clears the Node-attributed findings" is **false as written**. All seven fixable CRITICAL/HIGH in the built image are in the *system* Node's bundled npm (`tar`, `undici`, `brace-expansion`, `ip-address`), and **24.19.0 clears none of them** — its npm 11.17.0 carries `tar` 7.5.16, still below the 7.5.19 fix. No released Node 24 ships a clean npm tree. #38's gate therefore needs a decision this clause does not supply: scope it to `os-pkgs`, suppress the npm tree with D7's justification discipline, or drop the bundled npm. Zero fixable CRITICAL/HIGH come from OS packages.

Evidence: [`docs/research/core-base-measure/core-image-2026-08-04.md`](../research/core-base-measure/core-image-2026-08-04.md).

**D11 — The CVE gate fails on *fixable* CRITICAL or HIGH only.** Trivy runs on the built Core image in `ci` and on every weekly rebuild. Unfixed findings do not fail the build — there is nothing to do about them, and failing on them teaches people to ignore the gate. Medium and low are reported, not gating. ([#8 §5](https://github.com/actana/control/issues/8))

**Amended 2026-08-04 by [#38](https://github.com/actana/control/issues/38), which built the gate and answered the question D10's amendment left it.** The clause stands; two things it did not say are now decided, and both are suppressions that must be named as such.

> **The system Node's own bundled npm tree is scoped out of the gate — reported on every run, never gating.** Of the three options D10's amendment offered, this is a fourth that is narrower than "scope it to `os-pkgs`": the exclusion is the single path `usr/local/lib/node_modules/npm/`, so the Core's own shipped tree under `/opt/actana` and anything installed beside npm still gate. It is chosen because the residue is not payable by any PR. Re-measured on the shipped image: all seven fixable CRITICAL/HIGH are in that directory, and **no released npm clears them** — npm 12.0.2, the newest there is, ships `brace-expansion` 5.0.7 against fixes at 5.0.8 and 5.0.9, and `ip-address` 10.2.0 against a fix at 10.3.1. "Bump Node" was already measured false; "bump npm" is measured false too, though it would clear four of the seven including the only CRITICAL, and that bump is [#51](https://github.com/actana/control/issues/51)'s to weigh on the weekly rebuild, not a PR gate's. This is a second suppression, bounded by path rather than by CVE, and its cost is that a *new* finding in that tree is silently non-gating too. It is deliberately **not** in the allowlist file, so D7's "one file, one entry" survives literally and the two suppressions stay visibly different in kind.
>
> **The allowlist is `.trivyignore.rego`, not `.trivyignore`, and that is forced.** D7 and D37 both say "one entry, for `linux-libc-dev`". Measured: Trivy's `.trivyignore` and `.trivyignore.yaml` match on CVE **id** only — a package name in either parses cleanly, filters nothing, and warns about nothing, so the file those clauses describe is not expressible in that format and the version that looks like it is, is silently a no-op. A one-rule Rego ignore policy is the only Trivy mechanism that expresses it, and the scan asserts the suppression actually took effect rather than trusting that it did. Read D7 and D37's "`.trivyignore`" as naming the repository's single allowlist, not the file format.

Implementation: [`.trivyignore.rego`](../../.trivyignore.rego), [`scripts/scan-core-image.mjs`](../../scripts/scan-core-image.mjs), and the policy write-up in [`docs/ci-cd.md`](../ci-cd.md) (G3's destination, until [#59](https://github.com/actana/control/issues/59) moves it to `docs/contribute/`).

**D12 — The Core runs as `core`, uid 1000, gid 1000, always.** Ubuntu 24.04 ships a stock `ubuntu:x:1000:1000` user and a group called `operator`, so `useradd` without explicit ids lands on 1001:100 — which breaks every bind-mounted repo, since files a Harness writes would be owned by a uid that exists nowhere on the operator's host. The stock user is removed and the ids are pinned explicitly, with the reason written beside them. `NPM_CONFIG_PREFIX=/home/core/.local`. `NOPASSWD` sudo is kept for `core`: without it a mid-session "install a system dependency" is a dead end on a machine whose entire purpose is arbitrary work.

**Overriding `user:` in compose is not supported.** It half-works and that is worse than a refusal — sudoers is per-name/uid so an overridden uid gets no sudo, and `NPM_CONFIG_PREFIX` points at a home it cannot write, so `actana harnesses install` fails even if sudo is widened. A host whose login user is not uid 1000 has two supported answers: `chown -R 1000:1000` the bind-mounted directory, or use a named volume so the Core owns the repos. **Documentation obligation:** under rootless Docker/Podman the engine maps container uid 1000 to a host subuid, so plain `chown 1000` is the wrong advice there — `podman unshare chown` or `--userns=keep-id` is. `docs/install/docker.md` must say so. *(Resolves C1 and C7; `core` over `operator` because the Operator is already the human who logs into the Panel.)*

## C. The Core as a container

**D13 — The image *is* the install; `actana setup` is bypassed entirely.** No versioned tree, no `current` symlink, no unit file, no `loginctl enable-linger`, no third `ActanaServiceManager`. Every job `setup` does is already done by something else in a container: the image tag is the versioned tree, `ENTRYPOINT` is the unit, `restart: unless-stopped` is lingering, `docker compose pull && up -d` is `actana update`. A degraded no-systemd `setup` would be a second lifecycle path that nothing supervises. **The metal path is untouched** — `install.sh` + `actana setup` + systemd remains the story for a real machine. This is a second distribution, not a replacement. ([#9 §1](https://github.com/actana/control/issues/9))

**D14 — `tini` is PID 1; the daemon is its child.** `ENTRYPOINT ["/usr/bin/tini", "--"]`, `CMD ["actana", "daemon"]`. node-pty forks a shell and the shell forks a Harness; when a shell exits while its Harness is still running, that process reparents to PID 1, and libuv only `waitpid()`s children Node spawned itself — so a long-lived Core accumulates zombies until the PID table fills. Baked into the image rather than `--init`/`init: true`, because those are opt-in and anyone copying a bare `docker run` would get the broken configuration by default. *(Resolves C2. #8 §0's prose — "the shipped Core image runs `actana daemon` as PID 1" — is **amended, not merely supplemented**. Its actual argument was against **systemd** as PID 1 under `--privileged` + `cgroup: host`, and tini satisfies that argument completely: it is 10 kB, it is not a supervisor, and `tini 0.19.0-1` is in noble at exactly the `/usr/bin/tini` path #9's ENTRYPOINT assumes.)* ([#9 §2](https://github.com/actana/control/issues/9))

**Amended 2026-08-04 by [#46](https://github.com/actana/control/issues/46), which booted the image and looked.** The clause said "the daemon is PID 2", and the daemon is **not** PID 2 in the shipped image — the number was never the invariant. What D14's argument needs is a topology: `tini` at PID 1, and the daemon as tini's child rather than PID 1 itself. The integer is not the launcher's to promise — `bin/actana` is `#!/bin/sh` and runs `command -v`, `readlink` and a `cd -P` subshell before it `exec`s, each forking a PID that exits again, so a change to `core-tarball.mjs`'s launcher moves the daemon's number without touching anything this clause is about. The smoke asserts the property (`/proc/1/comm` is `tini`, and a `node` whose PPID is 1), which fails in the one case D14 exists for — a daemon that *is* PID 1, reaping nothing — and in no other. `docs/ci-cd.md` and `docs/images/core.md` are corrected in the same commit.

**D15 — Three documented variables; the minimum for a working Core is one.** `ACTANA_PUBLIC_HOST` (**required**), `ACTANA_PORT` (8443), `ACTANA_LABEL`. The image never guesses its public host: `choosePublicHost()` picks the first routable IPv4, which is reasonable on metal and a trap in a container, where a bare `docker run` has a container-ID hostname and a guessing default would silently change the cert SAN on every recreation. Baked as private image constants and **not** part of the operator contract: `ACTANA_CONTAINER=1`, `AC_CORE_REMOTE=1`, `AC_CORE_LINK_HOST=0.0.0.0`, `AC_USER_DATA_DIR`, `AC_APP_PATH`, `AC_CORE_MATERIAL_FILE`. `EXPOSE` reads from the same `ARG` as `ACTANA_PORT` rather than being hardcoded. *(Resolves C6 — #8's Dockerfile carried none of this env contract, which would have produced exactly the guessing Core #9 refuses by design.)* ([#9 §3](https://github.com/actana/control/issues/9))

**D16 — Container mode is detected by the baked `ACTANA_CONTAINER=1`, never by sniffing `/.dockerenv`.** `setup`, `start`, `stop`, `restart`, `update`, `uninstall` and `logs` **refuse and name the Docker equivalent**. `status`, `token`, `token regenerate`, `harnesses`, `daemon` work unchanged. `status`'s auto-start row reports the container's restart policy rather than a unit that does not exist — as *where to read it* (`docker inspect -f '{{.HostConfig.RestartPolicy.Name}}'`), because the policy is set on the host and no process inside the container can read `HostConfig` back. *(Amended while implementing [#39](https://github.com/actana/control/issues/39): `logs` joins the refusal list, which the original clause left unassigned. It cannot work — it execs `journalctl --user -u actana-core.service`, and the image has neither journal nor unit — so leaving it out would have shipped one verb that fails with a missing binary instead of naming `docker compose logs -f`. #39's own "name the Docker equivalent" examples already included `docker logs`.)* `token regenerate` keeps its meaning but not its restart: there is no unit to bounce and the CLI is not the daemon's parent, so it writes the new material and tells the operator the restart is theirs — the old identity is live until the container comes back, and saying otherwise would be a lie. ([#9 §1](https://github.com/actana/control/issues/9))

**D17 — Pairing is a first-run mint persisted into the volume.** Missing `material.json` → mint CA, server cert, client cert, bearer secret and `coreId`, **persist**, write `registration-blob.txt` beside it, print the blob once to stdout in human-readable form (not behind the `@@…@@` sentinel), with `ACTANA_LABEL` feeding the `label` field that path currently hardcodes to `""`. Present → load, start, print nothing. Restart is a no-op for pairing; `docker compose down -v` is the only thing that unpairs. Pre-seeding material via env or a mounted secret is rejected — it would need a generator that runs outside a Core and would put private keys in compose files. **One code change is required:** the daemon's existing fresh-material path mints and prints but does not persist, because that was `actana setup`'s job; it must persist when `AC_CORE_MATERIAL_FILE` is set and the file is absent. ([#9 §4](https://github.com/actana/control/issues/9))

**D18 — A changed public host re-issues the server cert from the kept CA; it never re-mints identity.** Today `resolveMaterial()` re-mints everything when the recorded public host differs — new CA, new certs, new `coreId`, every paired Panel locked out — and in a container a typo'd env var fires that. Instead: keep the CA key and cert, the bearer secret, the `coreId` and the Panel's client cert, and sign a fresh server cert for the new SAN. The blob the Panel already holds still validates. A full re-mint never rescued the moved-Core case anyway, since the Panel dials the endpoint stored from the old blob regardless — which is why a move also rewrites the volume's `registration-blob.txt` (D17) with a token for the new address: the endpoint is the one half re-issuing cannot reach, and the operator needs it in hand to re-address their Panel. Two things bound the re-issue, both because a wrong SAN is as unreachable as a stale one: material predating the recorded host is re-signed silently rather than announced as a move that may not have happened, and a public host the operator never declared — the bind address standing in for one — never re-signs anything. `actana token regenerate` remains the deliberate way to revoke a leaked blob. ([#9 §5](https://github.com/actana/control/issues/9))

**D19 — One volume, the whole home: `core-home:/home/core`.** It holds the identity, the recorded config, the SQLite, **and every Harness's own credentials** (`~/.claude`, `~/.codex`, `~/.config/opencode`, …). The mount is the home and not a narrow `/var/lib/actana` precisely because Harnesses write all over `$HOME` and enumerating them is a losing game — a narrower mount means every `docker compose up` logs the operator out of Claude Code. One mount, one backup target. On repos the Core takes no position: bind mount is what the reference compose demonstrates, clone-in-shell needs nothing new, a named volume is available. *One partial state is genuinely broken and the single volume makes it unreachable:* keeping `material.json` while losing the SQLite leaves the Panel's per-Core `lastEventId` cursor ahead of the Core's max event id, so replay returns `[]` and the Panel goes quiet with nothing erroring. Anyone hand-restoring one file without the other must reset the Panel's cursor. ([#9 §6, §7](https://github.com/actana/control/issues/9))

## D. The Panel image

**D20 — Distroless runtime, full-Node build stage, digest-pinned.** `gcr.io/distroless/nodejs24` (Debian 13, Node 24.18.0), built by an untouched `node:24-*` build stage whose CVEs never ship. **Measured on the built image: 192 → 14 total, 174 → 12 OS, 18 → 2 library; zero CRITICAL and zero HIGH from the OS.** The 12 remaining OS findings are `libc6` (11) and `zlib1g` (1) — nothing else in the image has a CVE because there is nothing else in the image. Size 633 → 545 MB; this is a CVE story, not a size story, and must not be sold as one. Pinning is by digest only: the repository carries 6,980 tags and **not one contains a version number** — four mutable names plus opaque build SHAs — so whatever Dependabot/Renovate config lands must update digest pins for a registry with no semver, or the image silently drifts its Node patch version between builds. ([#10](https://github.com/actana/control/issues/10))

**D21 — `USER 65532:65532`, numeric, on the default tag. This closes #6's open item on rootless/non-root posture for the Panel.** The `:nonroot` tag is **not** forced: every distroless variant, default tag included, ships `nonroot:x:65532:65532` in `/etc/passwd`, so `USER 65532:65532` on the default tag drops privilege exactly as the tag would — and it keeps the security posture stated in our Dockerfile instead of inherited from a tag name. Numeric is load-bearing, not style: Kubernetes' `runAsNonRoot` admission check cannot resolve a username and fails the pod rather than the check. The `node` user (uid 1000) no longer exists, so anything referencing it by name breaks. ([#10 q4, item 4](https://github.com/actana/control/issues/10))

**D22 — `/data` is created by `COPY --chown=65532:65532` from a staged directory, never by a staged `chown`.** Measured: `COPY` recreates the destination directory itself as `root:root 0755` and discards the source directory's ownership *and* mode; ownership only survives for entries *inside* a copied tree. Docker seeds a fresh named volume from the image's content **and mode** at that path, so getting this wrong gives every new deployment a `/data` the Panel cannot write to. The prototype's first build shipped exactly that bug. This is the single clause most likely to break a real deployment if it is skimmed. ([#10 q4, item 1](https://github.com/actana/control/issues/10))

**D23 — Distroless changes the invocation in three ways that fail quietly.** `CMD ["bin/panel.mjs"]` — the script path alone, because `node` is the ENTRYPOINT and leaving `"node"` in the array makes node try to run a file literally named `node`. `HEALTHCHECK` uses the **absolute** `/nodejs/bin/node`, because HEALTHCHECK argv bypasses ENTRYPOINT and distroless's `PATH` does not contain `/nodejs/bin` — measured, the naive `["node", …]` form reports UNHEALTHY even for a script that cannot fail. And the healthcheck must be **verified to survive the CI builder**: podman silently drops it without `--format docker`, so `docker/build-push-action` with multi-platform output must be confirmed to preserve it, or the published image ships without a healthcheck while local builds look fine. ([#10 q2, q3, item 8](https://github.com/actana/control/issues/10))

**D24 — Four assertions in `scripts/__tests__/panel-image.test.mjs` become false and each needs a deliberate replacement, not a patch to green.** "builds on the exact Node CI tests against" (distroless cannot satisfy it, and the runtime Node genuinely differs from CI's), "is multi-stage with a slim runtime", "runs as the unprivileged `node` user", and — passing only by luck — "starts the same entry the bare-node path documents". The replacements are the invariants in D20–D23: a digest-pinned distroless final stage, numeric `USER 65532:65532`, `COPY --chown` on `/data`, an absolute-path healthcheck, and `CMD` without a `node` element. ([#10 item 5](https://github.com/actana/control/issues/10))

**D25 — Build and runtime stages are aligned on Debian 13.** Today's prototype builds on bookworm (glibc 2.36) and runs on trixie (glibc 2.41). It works — glibc is backward-compatible in that direction, and a `better-sqlite3` compiled in the build stage was verified loading at runtime — but it is an unstated dependency, and doing it in the *other* direction would break. The build stage moves to `node:<ci-node-version>-trixie` so both stages are Debian 13. If that build fails, staying on bookworm is acceptable **only with a comment stating the asymmetry and its direction**. ([#10 item 7](https://github.com/actana/control/issues/10))

**D26 — `gcr.io` is a third registry in the build path, and that is accepted.** #6 settles Docker Hub primary / GHCR mirror for *publishing*; pulling the base from Google's registry is a separate availability and rate-limit dependency on every build. Recorded so it is a known dependency rather than a surprise during an outage. ([#10 item 10](https://github.com/actana/control/issues/10))

## E. Release

**D27 — The version resets to `0.1.0`, and the 102 local tags are deleted.** `actana/control` is one squashed commit with **zero tags and zero releases**; the `0.49.0` in four manifests belongs to a product that is not in this repository, and a first-ever release numbered `0.50.0` would tell an operator the thing has been through fifty iterations when it has shipped zero times. 1.0.0 is also unavailable: it would be a stability promise, and the wire contract, on-disk layout, image contract and asset names are all being rewritten by this effort. **The 102 local tags are deleted, not merely left unpushed** — they sort above `0.1.0`, and `release.yml` triggers on `v*`, so a single `git push --tags` would both re-import the upstream Electron history into a deliberately squashed repo and fire 102 release runs. This is the sharpest edge in the whole effort and it is one command to remove. ([#13 §0, §1](https://github.com/actana/control/issues/13))

**D28 — A tag publishes exactly three assets and two multi-arch images.** `actana-core-0.1.0-linux-x64.tar.gz`, `actana-core-0.1.0-linux-arm64.tar.gz`, `SHA256SUMS`. Three rather than five because macOS Core targets are dropped, which means: the release matrix halves to two legs, `CORE_TARGETS` drops its two darwin rows, and **`compose-core-shasums.mjs --expect 4` becomes `--expect 2` deliberately** — that guard is what makes a silently missing architecture a red build rather than a checksum file covering half the release. `install.sh` must **fail early on Darwin at detection**, with the message the Windows branch already uses; today it maps `darwin` → `mac` and produces the late, misleading "release v0.1.0 has no build for mac-arm64". ([#13 §2](https://github.com/actana/control/issues/13))

**Amended 2026-08-06 by [#90](https://github.com/actana/control/issues/90), which gives macOS a first-class on-device Core.** The asset count and the "no macOS legs" half of this clause are **withdrawn**; the reasoning that produced them is not. What D28 was defending is *per-PR* CI cost — three macOS legs were 72% of the old bill (D35) — and that is untouched by a leg that only ever runs on a release tag. Read the clause as governing the guard, not the number:

> **A tag publishes exactly four assets and two multi-arch images.** `actana-core-<version>-linux-x64.tar.gz`, `actana-core-<version>-linux-arm64.tar.gz`, `actana-core-<version>-mac-arm64.tar.gz`, `SHA256SUMS`. `CORE_TARGETS` carries one darwin row, `mac-arm64`, and **`compose-core-shasums.mjs --expect` is `3`, the count of those targets, deliberately** — that guard is what makes a silently missing architecture a red build rather than a checksum file covering part of the release. The mac tarball is built by `release.yml`'s `tarball-macos` job on an Apple-silicon runner, behind the **`macos-release` GitHub environment's required reviewers**: the release pauses there until a reviewer has run [the macOS pre-release checklist](../core-macos-prerelease-checklist.md) on real hardware and approved. `github-release` needs that job, so the whole release waits — a `SHA256SUMS` covering a subset of the architectures the docs promise is worse than a release that is late. **Zero macOS in per-PR CI stands**, and no weekly canary is added (deferred).

`install.sh` still refuses Darwin **at detection** where there is no asset — but only for an **Intel Mac**, and by name rather than with the generic unsupported-OS message: `mac-x64` is an asset that will never exist, and the Core image is the supported path there. `releaseTargetFor` in `packages/core/src/actana-release.ts` returns `null` for `darwin`/`x64` for the same reason, so `actana update` on an Intel Mac fails at detection rather than against a missing asset. Intel Macs, Windows, code signing and notarization all remain out of scope.

**D29 — `install.sh` stays on `raw.githubusercontent.com/actana/control/main/install.sh` and is not a release asset.** The asset form would buy coherent pinning, but it makes a broken installer fixable only by cutting a release — and the installer is precisely the component that runs on machines nobody tests, under other people's `sh`, `curl`, `tar` and `awk`. The cost is paid explicitly as a rule that belongs in any future release review verbatim:

> `install.sh` on `main` must work against **every published release**. Its contract with a release is three things: the `SHA256SUMS` asset name, the `actana-core-<version>-<target>.tar.gz` asset name, and `bin/actana` inside the extracted directory. Changing any of them is a breaking change to the installer contract requiring a major bump plus a documented migration — not a patch-level edit to a shell script.

Until the repo is public that URL 404s, so the documented one-liner cannot run end to end. That is not a coverage gap — `install-sh.test.mjs` runs the real script against `fixture-release-server.mjs` in under a second and the e2e runs the real one-liner against a real systemd machine. Exactly one thing stays untested until launch: **that GitHub serves the file at that URL.** It belongs on the go-public checklist. ([#13 §3](https://github.com/actana/control/issues/13))

**D30 — Image tags: `0.1.0` and `latest` from a version tag, `edge` and `sha-<short>` from `main`. No `0` / `0.1` ladder.** Under semver a `0.x` minor bump *is* the breaking change, so a moving `:0` tag would silently ship a break to anyone pinned to it for the entire life of `0.x` — a lie by construction. `:edge` survives as a tag but dies as a workflow: `images-edge.yml` is deleted and its jobs become a push-to-`main` branch condition inside `ci.yml`, which already calls the same reusable `container-image.yml`. That keeps the promise that the bytes a PR validates are built exactly the way the bytes a release publishes are. ([#13 §4](https://github.com/actana/control/issues/13))

**D31 — One Docker Hub PAT, and a missing credential fails on `actana/control` while still skipping on forks.** An OAT can push images but cannot call `POST /v2/users/login` for descriptions — it returns *"Cannot log into an organization account"* — so choosing OAT means paying for a Team or Business subscription **and still** provisioning a PAT. One PAT does both; `DOCKERHUB_DESCRIPTION_USERNAME`/`_TOKEN` are deleted. Today the credential check skips everywhere, which is right for forks and wrong for the canonical repo: a release that never reached the primary registry must not report success. The honest cost is that the token belongs to a person and dies with that account — a documented rotation step in `contribute/repo-setup.md`, not a design flaw. **Present-but-broken keeps today's behaviour deliberately:** publish GHCR completely — per-arch tags *and* manifest — then fail the run at the very end, because failing early would strand GHCR with per-arch tags and no manifest. ([#13 §5](https://github.com/actana/control/issues/13))

**D32 — "Docker Hub is the primary registry" means the canonical place a user is told to pull from, not the publish order. Do not reorder the pushes to match the word.** The workflow builds under the GHCR name, pushes GHCR first, and requires GHCR to complete — deliberately, because GHCR authenticates with the workflow's own `github.token` and therefore *cannot* fail on credentials. This clause exists because the wording in #6 item 8 invites exactly that "fix". ([#13 §5](https://github.com/actana/control/issues/13))

**D33 — Descriptions fold into `release.yml` and fire on the release, not on a docs push.** `dockerhub-description.yml` is deleted; its `sync()` body moves verbatim, including the `curl`-not-a-third-party-action posture, which stays because this step handles a credential that can rewrite the public face of both images. `workflow_dispatch` covers fixing a typo without cutting a release. **`docs/images/core.md` is rewritten, not edited** — every load-bearing sentence in it is false under D5–D19: it leads with a "not a production deployment" banner, says there is no supported container deployment of a Core, and documents systemd as PID 1, `--privileged`, the host cgroup and a hardcoded `--public-host core`. The `ai.actana.image.role=development-fixture` label goes with it. `docs/images/panel.md` needs three edits only. Note `docs/images/**` is a **frozen path** — a workflow and a test hardcode it — so it does not move in the docs restructure. ([#13 §6](https://github.com/actana/control/issues/13), [#15 F2](https://github.com/actana/control/issues/15))

**D35 — 26 PR jobs become 13, at ~5 min wall clock and ~89 → ~17 billed minute-equivalents.** The diagnosis matters for what gets cut: nothing in CI is slow — the slowest job is 3.5 min and every container e2e leg is 1.0–1.5 min — CI is expensive because of job count and macOS billing at 10×, and **72% of the bill is three macOS legs** whose product justification #6 already deleted. **D36 — One installer e2e, and the Core image smoke does not replace it.** The one-liner becomes the *entry point* of the setup e2e rather than a separate suite, which is strictly more coverage at roughly the cost of one and removes a seam rather than adding one. Axes are `distro × arch`: Ubuntu and Debian at x64 on PR, because PAM, polkit and the logind rules that decide whether a sudo-less `systemctl --user` and `loginctl enable-linger` work at all are exactly what differs between distros; arm64 moves to the tag run, because the arch-sensitive risk is prebuilt native modules and `core-tarball-smoke` already boots the arm64 tarball on an arm64 runner every PR. **D37 — Dependency-audit policy: three populations, three owners. This closes #6's open item.** Stated so nobody later "simplifies" one into another — `pnpm audit` cannot see the base image at all, and Trivy has no dev/prod notion, so neither substitutes for the other:

|---|---|---|

| Dev-tree packages | `pnpm audit --audit-level high`, opens an issue | weekly |
| OS layer + shipped `node_modules` in the image | Trivy, fails on **fixable** CRITICAL/HIGH | PR, on the image build |

**The allowlist is one file and one entry:** the checked-in `.trivyignore` from D7, for `linux-libc-dev`, with its justification beside it. Nothing else is suppressed anywhere. *(Amended 2026-08-04 by [#38](https://github.com/actana/control/issues/38) exactly as D7 is: the allowlist is still one file and one entry — `.trivyignore.rego` — but the gate carries a second, path-bounded suppression outside it. A check that is red for reasons unrelated to the change in front of it is a check everyone learns to click past. **D39 — Two already-diagnosed fixes are required before `main` can be green, and neither is a decision.** `pnpm update -r postcss @babel/core` (lockfile-only: 8.5.15 → 8.5.25, 7.29.0 → 7.29.7) — until it lands, `dependency-audit` stays red even after D37, because the `postcss` high genuinely ships. ## G. Docs and repo shape

**D40 — `deploy/` holds both images and the one reference compose.** `deploy/core.Dockerfile`, `deploy/panel.Dockerfile`, `deploy/docker-compose.yml`. The root `Dockerfile` moves — #6 item 7's thin root does not list it, and "two container images" should not mean finding one at the root and one two directories down. `deploy/dev/` is deleted entirely: `core.Dockerfile`, `core-provision.sh`, `core-provision.service`, its compose and its README all exist to fake a systemd machine so the tarball has somewhere to install, which is the design being killed. *This clause exists because #9 deleted the only Core Dockerfile the repo has without naming a replacement, and #15's README then opened with a `docker compose -f deploy/dev/docker-compose.yml up` pointing at the deleted file (C3, C4).* The moves are not free and must be one deliberate change: `container-image.yml:174,179,194,203`, `panel-image.test.mjs:20,29,47,188,194,217-226,241`, `smoke-panel-image.mjs`, `docs/images/core.md`, and the prose links in `README.md`, `CONTRIBUTING.md`, `docs/README.md` and `docs/ci-cd.md` all name one of the old paths.

**D41 — There is one reference compose, and it has no TLS terminator.** Panel + Core on one network, plain HTTP, `restart: unless-stopped`, `core-home` volume, no published Core ports — only the Panel reaches it, over the compose network. Operators bring their own nginx / Traefik / edge; the Panel speaks plain HTTP by design (ADR 0010 — "the Panel itself never grows certificate code"), so the reference's job is to name the port to point a proxy at. The Caddy + Let's Encrypt service is dropped, which also collapses the public-vs-local file split. **This is the browser-facing edge only — the core-link's mTLS is untouched** (ADR 0002): the Core presents a self-signed server cert from its own CA and requires the Panel's client cert; that material is minted by the Core, travels in the registration blob, and is never something an operator supplies or renews. `ACTANA_PUBLIC_HOST=core` is a *compose* fact in a file the operator edits, not an image fact they cannot. ([#9 §9](https://github.com/actana/control/issues/9))

**D42 — The docs tree is task-shaped: 81 files → 55, grouped by what the reader came to do.** `install/ operate/ reference/ architecture/ adr/ contribute/ agents/ research/`, a 58-line README replacing today's 224, `CONTEXT.md` + `domain-model.md` merged into `docs/architecture/vocabulary.md`, and a disposition for every existing file. Two fixed points: **`docs/adr/` does not move** (nesting it under `architecture/` would cost a repo-wide citation sweep on top of the eleven-file rename already ordered for that directory, and it is the convention every ADR tool assumes), and **`docs/images/` is frozen** (D33). ([#15 §1, §3, F2, F3](https://github.com/actana/control/issues/15))

**D43 — Root gains a 3-line `CONTEXT-MAP.md`; it is not optional.** Deleting root `CONTEXT.md` without it does not make the glossary invisible — it makes the `/domain-modeling` skill **silently recreate an empty one** the next time any session resolves a term, so the repo grows a second competing glossary by itself with no PR to catch it. `CONTEXT-MAP.md` is the skill's own supported indirection, and its entries are ordinary markdown links, so the target needs no special filename and future sessions maintain `docs/architecture/vocabulary.md` in place. ([#15 follow-up](https://github.com/actana/control/issues/15))

**D44 — ADR numbering is settled: 0013 rename, 0014 no source-control surface, 0015 the fixed look, 0016 this file.** #12 and #17 both independently claimed 0013. #12's rename takes the low number because it is the sweep everything else applies. **Consequence:** #17's `schema-bootstrap.ts` citation table shifts up one — line 518 → ADR **0014**, line 527 → ADR **0015**. ([#15 F1](https://github.com/actana/control/issues/15))

**D45 — `AGENTS.md` and `docs/agents/` keep their names; only their contents get the vocabulary pass.** `AGENTS.md` is an external filename convention that coding CLIs discover by that exact name, so #12's retirement of "Agent" does not reach it — the same logic that exempts macOS LaunchAgent. **This is the highest-risk vocabulary in the repo:** these files are what a coding harness reads before it writes anything, so a file still teaching "Harness = the machine" will keep producing the old vocabulary in every future session and will look authoritative doing it. `docs/agents/domain.md` must land in the same PR as the `vocabulary.md` merge, not after it. ([#15 §6](https://github.com/actana/control/issues/15))

**D46 — 63 files are deleted after five facts are promoted, and the archive is not git history.** #17's test — *does this document a decision or constraint that is still true, and is it recorded nowhere else?* — is failed by all but five facts: K1 (Panel owns no source-control surface → ADR 0014 + two `vocabulary.md` rows), K2 (one fixed look from Actana Studio → ADR 0015 + an anchor comment at the `@theme` block), K3 (no code signing and *why it is safe* → `contribute/ci-cd.md`, plus repointing `install.sh:295` which currently cites a file being deleted), K4 (`actana.ai` is authoritative; fix `actano.ai` in ADR 0007), K5 (Terms of Service needs legal review → a tracker issue, deliberately given no doc home so it stays a task). Ten in-repo references must be repointed in the same PR, including nine `schema-bootstrap.ts` citations per D44.

> **#6 frame item 10's premise is false as written and must be restated before anything is deleted on the strength of it.** It justifies the deletions with *"git history is the archive."* `actana/control` is **one squashed commit** — there is no history on it. The archive is this working clone and the `azure` remote. `repo-template/` is the sharpest case: it is untracked, exists only in this clone, and is in no git history anywhere, so **deleting it destroys it** — it moves out of the working tree to its own home *first*, and only then is removed.

([#17](https://github.com/actana/control/issues/17), [#13 §1 aside](https://github.com/actana/control/issues/13), [#15 §5](https://github.com/actana/control/issues/15))

## What is genuinely still open

Recorded so none of it is mistaken for decided, and none of it is re-discovered as new:

- **Required approvals on the `main` ruleset — 0 or 1.** A live trade-off for a solo maintainer: `1` means a solo maintainer cannot merge without a second account or a bypass, which contradicts "no bypass actors". [#16](https://github.com/actana/control/issues/16) owns it. ## Sequencing

Four ordering constraints, all load-bearing:

1. **The rename sweep goes first.** #13, #14 and #15 all apply it, and fifteen paths in the docs tree encode the new vocabulary in their filenames.
2. **The docs tree cannot land before the Core Dockerfile has a path.** `install/docker.md`, the README's one-command block and the frozen `docs/images/core.md` must all name a compose file and a Dockerfile that exist (D40).
3. **#17's promotions land before #17's deletions**, so no citation is ever dangling at a commit boundary. `repo-template/` moves out of the clone before it is removed from it (D46).
4. **`main` is protected last.** Every implementation session after that works through PRs — which is the point, but it must not land before the required status checks have names that will still exist ([#16](https://github.com/actana/control/issues/16)).

The ticket-by-ticket breakdown, dependency graph and what runs in parallel live on the implementation map — [#23, *Build the 0.1.0 shape*](https://github.com/actana/control/issues/23) — not here. That is work tracking, and it does not belong in a permanent record.
