# The Core detects its own harness status

A Session card renders title and status from the owning Core's task snapshot, which is right — but nothing ever changed that snapshot after the row was created. The Core spawned harness PTYs without installing the harnesses' lifecycle hooks and exposed no endpoint for a hook to reach, so the documented hook → status mapping was dead for every Core-owned Session; it never settled a task whose PTY exited; and title generation ran only against the Panel's local store, which has no such row. This ADR records the contract and boundary changes that fix it, because they change the wire, move state across the Panel/Core boundary, and add a listener to the Core.

**Detection moves to the Core, whole.** The harness runs on the Core's machine, so the Core is the only process a hook on that machine can reach; the Core owns the row (ADR 0004), so it is the only process that can write the answer; the harness binaries the title generator shells out to in print mode exist only on the Core. Every step — hook receipt, status write, event append, title generation, PTY-exit settle — happens inside the Core process, and a Panel learns about all of it as an Event replayed off its cursor. Nothing round-trips through the Panel, and no Panel needs to be connected for a Session's status to be correct.

**The receiver is loopback HTTP on an ephemeral port, with a token the Core mints per boot.** It cannot be a route on the core-link listener: in remote mode that server sets `requestCert: true, rejectUnauthorized: true` and binds the Core's public host, so it demands a Panel client certificate that a hook subprocess on the same machine cannot present. HTTP rather than a unix socket because every vendor's hook config takes a shell command and assumes `curl`; what a socket would have bought is bought instead by binding `127.0.0.1` only and by the bearer. The token lives in memory and reaches the PTY through its environment, so the hook file on an operator's disk holds no secret and stays valid across a restart that mints a new one. The port is `0` — the OS picks it — and joins `getProtectedPorts`, so the Core's own port-kill path cannot take the receiver down and strand every Session's status.

**`CORE_LINK_PROTOCOL_VERSION` → 0.12.0.** Three additions. `titleManuallySet` on `CoreLinkTaskSnapshot` and its `update` mutation: without it the Panel synthesized `false` for every Core-owned row, so an operator's rename was generator fair game again on every reload. `claudeSessionId` on both, because the ported pipeline's foreign-session guard reads it and the resume path was writing a fresh session id into the Panel's database, leaving the Core's column holding a dead one. `hooksReportTurnStart` on the `spawned` response, below. No SQLite migration rides along — `title_manually_set` and `claude_session_id` have been in the shared schema bootstrap since the fork; only the wire and the Core's readers and writers of them are new.

**`hooksReportTurnStart`, not `hooksInstalled`.** The Panel's terminal-input fallback stands down on this and nothing else, and the distinction is load-bearing: Cursor accepts our hooks file but never fires `beforeSubmitPrompt`, and Codex refuses to run newly-installed hooks until the operator reviews them with `/hooks`. Both report a turn's *end* and leave its *start* unannounced, so exempting them on "hooks were installed" produces a Session that sits on `ready` for its whole first turn. The narrow question is the one the Panel actually needs answered.

**One write seam.** `CoreTaskWriter` is the single path for the Panel's `tasksMutate` frame and for the Core's own hook / exit / title writes, so a row cannot move without the event that describes it landing in the same log.

## Considered Options

- **A unix domain socket for the receiver (rejected).** Defensible on a shared machine, and it would need no bearer. Rejected on the cost of the alternative it forces on every hook of every harness, forever: `curl --unix-socket` is not what a vendor's hook documentation shows, not what an operator debugging a hook will type, and not guaranteed present in whatever shell a harness spawns. Loopback plus a bearer plus an unguessable port gets to the same place through a door every vendor already documents.
- **A route on the existing core-link listener (rejected — not actually available).** It would have needed no new listener at all. It cannot work: mTLS demands a client certificate the hook subprocess has no way to hold, and the listener binds the public host rather than loopback.
- **A fixed hook port (rejected).** Easier to document and to firewall. Rejected because it must then be kept clear of the core-link port by convention rather than by construction, and because a guessable port on a machine that runs other people's code is a target the OS will happily hand us an alternative to.
- **Passing the bearer down from the Panel, as the retired Electron design did (rejected).** There is no Panel in this hop any more. A token that has to survive a Panel reconnect, and be re-pushed to every running PTY when it changes, is state the Core can simply own.
- **Keeping status detection on the Panel and forwarding hooks to it (rejected).** It would have needed no Core listener, but every harness's hook would have to reach a Panel that may be on another continent, through a link the harness cannot authenticate to, to write a row the Panel does not have. It inverts ADR 0004 for no gain.
- **Reimplementing the subagent-activity state machine on the Core (rejected).** Its `Stop`-downgrade rule, 30-second recent-finish heal window, 3-minute drain grace and 2-hour expiry were each tuned against a documented failure mode. It moved to `@actana/shared` byte-for-byte instead, and the Panel's hook controller became an adapter over the same code, so the two hosts cannot drift.

## Consequences

- **Every Core must be updated alongside the Panel.** The minor moved, so a Core still speaking 0.11.0 is incompatible under the major.minor rule and renders as "needs update" (ADR 0005). That is the honest answer: an unbumped Core would hand a Panel a snapshot whose rename protection is silently absent, which renders as a Session the generator is free to rename out from under its operator.
- **The Core writes into the operator's workspace at every spawn.** `.claude/settings.local.json`, `.codex/hooks.json`, `.cursor/hooks.json`. Their own entries are preserved and ours are tagged `_acManaged` so a later spawn replaces exactly what an earlier one wrote. Entries left by the retired Electron app under `_mcManaged` are swept out on first write rather than left POSTing to an endpoint that no longer exists.
- **A harness family with no writer in the registry is not an error.** It gets no hooks, answers `hooksReportTurnStart: false`, and reaches `running` through the Panel's fallback and a settled status through the PTY-exit path. OpenCode is in that position today — its extension point is a plugin rather than a JSON hooks file, which is a different shape of work; it still shows the symptom this ADR removes for the other three, and is tracked as issue #101.
- **The Panel's PTY-exit patch no longer fires for a Core-owned row.** The Core sees the exit of the PTY it spawned whether or not a tab is open, and settles conditionally — a Session already `interrupted` keeps that status. The Panel's unconditional patch would have overwritten it and raised a spurious `session:finished` besides. It stays only for the Panel's own rows, whose PTYs no Core watches.
- **The Panel keeps a hook endpoint and a title generator for its own remaining local rows.** Both now run the shared code. Migrating those rows off the Panel's database is a separate piece of work.
- **The hook token is inherited by everything the harness spawns.** `AC_HOOK_TOKEN` rides the PTY's environment, so any child process — every command the harness runs, and anything those run — can read it and POST as any task on this Core. This is accepted, not overlooked: the blast radius is a wrong status or title on a card, the harness is already executing arbitrary code on this machine with the operator's account, and the alternatives (a per-task token minted at spawn, a nonce the receiver hands out) narrow the window without closing it, because the hook command itself has to be able to read whatever it presents. It is the same exposure the retired `MC_API_TOKEN` design carried. If the Core ever grows a hook route that can do more than move a card, this is the line to revisit first.
- **`session:finished` is appended, not consumed.** Routing the notification it raises is #20's job; this ADR only guarantees a Core produces the event on a real transition into `finished`, once.
