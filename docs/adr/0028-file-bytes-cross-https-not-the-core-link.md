# File bytes cross HTTPS, not the core link

The core link is the one multiplexed WebSocket between a Core client and a Core. It carries PTY streams, task mutations, hook events and notifications as framed JSON, and [ADR 0024 D1](0024-a-core-serves-many-clients-one-holds-a-sessions-write-lock.md) makes it the one connection per client — no per-task channels, no second socket.

[#129](https://github.com/actana/control/issues/129) phase 3 adds file transfer, and the obvious move is to put it on that socket. There is already a connection, already authenticated, already reconnecting, already multiplexed. **This record does not do that.** File bytes cross the Core's **HTTPS origin** — the same `https.Server` the WebSocket is mounted on, on the same port, behind the same client certificate and the same bearer — and not one byte of a transfer goes through a core-link frame.

The distinction this rests on: it is **one authenticated reach into one machine, with two protocols on it**, not two connections. `CoreConnection` already names both halves — `url` and `httpsBaseUrl`, off the same registration blob — and it named them before there was anything to answer on the second one.

## The decisions

**D1 — File bytes never cross the core link.** No `fileChunk` frame, no base64 payload, no `upload`/`download` request type. The core link's frame set is unchanged by this ticket, and that is the assertion, not a side effect.

Two reasons, and the first is the one that would be discovered in production rather than in review. **Head-of-line blocking:** the core link is one socket carrying every PTY's output for every Session a client is watching. A multi-gigabyte upload chunked into JSON frames puts thousands of large frames into that queue, and every terminal repaint behind them waits. The operator's symptom is not "the upload is slow" — it is *every terminal on that Core stuttering for the duration of a file copy*, which is an outage-shaped bug caused by a feature nobody asked to be interactive. **And base64 costs a third of the wire**, because a JSON frame cannot carry raw bytes. A 3 GB folder becomes 4 GB on the network, and it is paid twice — once in bandwidth and once in the CPU on both ends.

**D2 — The routes mount on the server that already terminates the WebSocket.** One `https.Server`, one `listen`, one certificate, one port. `defaultCreateServer` in `pty-core-link-server.ts` builds the TLS server and hands it to `ws`; it now also hangs a `request` handler on it. The WebSocket attaches to `upgrade` and the routes answer everything else, and neither knows about the other.

This is what keeps "one reach into one machine" true. **A second listener would be a second port**, and a second port is a second firewall rule, a second thing to forward, a second thing an operator's reverse proxy has to be told about, and a second thing that can be up while the first is down — a Core that is reachable for terminals and not for files, which is a state nothing in the system can express. The registration blob would have to grow a field for it, which makes every already-issued blob incomplete.

**D3 — Same certificate, same bearer, and the bearer is checked here too.** Every `/v1/…` request presents the pinned client certificate at the TLS handshake, exactly as the WebSocket does, and carries `Authorization: Bearer <bearer>` verified by the same `verifyBearer` the `auth` frame uses.

**mTLS alone is deliberately not the gate.** The client certificate says a Panel was paired with this Core at some point; the bearer says the pairing is *still current* and has not been superseded by a reissue. The core link requires both ([ADR 0002](0002-core-link-auth-and-transport.md)), and a file surface that required only one would be the weakest door in the building — and the one that moves whole directories.

**D4 — The capability is announced on `ready`, and `CORE_LINK_PROTOCOL_VERSION` does not move.** A Core that serves these routes puts `files: { version: 1 }` on its `ready` frame ([#129](https://github.com/actana/control/issues/129) F9). The protocol version stays where it is and no Core in any fleet becomes needs-update.

[ADR 0024 D11](0024-a-core-serves-many-clients-one-holds-a-sessions-write-lock.md) permits this only where the capability's *absence yields exactly today's behaviour*, and here that test is trivially satisfied in a way no previous capability could claim: **the surface is not on this protocol at all.** There is no frame added, none gated, and none whose meaning changes. A Core without the capability is a Core with no file routes — which is every Core that has ever shipped — and its core link is byte for byte what it was.

Both mismatch directions are therefore ordinary. An **older Panel against a newer Core** never reads the field and drives that Core exactly as it does today. A **newer Panel against an older Core** reads the absence and withholds the affordance rather than calling a route that would 404. `readFilesCapability` reads an unrecognised future version as absent for the same reason `readMultiConnectionCapability` does: the safe fallback is the behaviour that predates the capability, never a guess that version 2 is a superset of version 1.

The capability is announced **when and only when the routes are actually mounted**. Announcing one whose routes are not answering is worse than announcing nothing, because a client that reads the field stops feature-detecting and starts calling.

"Mounted" has to mean *answering*, and the first implementation of this ADR got that wrong in the one place nothing tested: `core-entry` handed the routes a bearer verifier that was always present and, on a loopback Core, always refused — so the default Core announced the capability and then answered `401` to every request against it. The rule the code now states in `core-files-wiring.ts`, and which a test asserts as a sentence, is: **the file routes are gated by a bearer when, and only when, the core link on the same server is.** A remote Core requires it; a loopback Core requires nothing, exactly as its core link requires nothing. Either way the routes answer, so either way the capability may be announced.

**D5 — Progress is a chunked NDJSON response body on the write path.** A `PUT` answers `200` with `application/x-ndjson` and one line per entry — `{path, size, mtime, mode, sha256, result}` — followed by a `done` line, streamed as the transfer happens rather than collected and sent at the end.

NDJSON rather than a JSON document because **this stream is expected to stop in the middle.** A document has to be well-formed to be parsed at all, so a transfer that fails on entry 4000 of 5000 would produce an unreadable body describing 3999 successes. A line-delimited stream is readable up to wherever it stopped, and the failure is simply the last line: `{"type":"error","code":…}`. The status line was spent on the first entry, long before the failure was knowable, and that is a property of streaming rather than a compromise.

**The read direction has no NDJSON stream, and that is not an omission.** A `GET` of a folder answers with the tar itself — the body is taken — and the tar's own headers already carry four of the five fields (`path`, `size`, `mtime`, `mode`) natively. The fifth is a digest of bytes the reader is receiving, so the reader computes it in the same single pass the writer would have, and gets the same answer. Bolting a manifest onto the read direction would mean either buffering the archive to hash it first, or appending a synthetic entry that `tar -xf` would extract into the operator's directory. Neither is worth what it buys.

**D6 — One write transfer per Project, refused immediately; reads unrestricted and concurrent.** A second `PUT` to a Project already being written is answered `409` with the code `transfer-in-progress`, naming which path is being written and since when. It is a refusal and not a queue.

A queue reads as the kinder option and is not. It holds an operator's connection open for however long a `node_modules` takes, produces no output while it waits, and then applies two people's intentions to one tree in an order nobody chose. The immediate refusal tells them the true thing while they are still looking at the terminal.

`409` plus a distinct `code` because the refusal has to be **distinguishable** — by status from a bad path (400) and a missing Project (404), and by code from any other 409 this surface might grow. A client that had to match on the prose would break the day somebody rewords it.

Reads are not gated at all: any number at once, including during a write. A read cannot corrupt anything, and a Core that made downloads queue behind an upload would make a busy Project unreadable for the duration.

**D7 — No size cap; a free-space precheck instead.** A Project takes whatever fits on the disk. What is checked before the body is read is whether it fits: the declared `Content-Length` against `statfs` on the Project's filesystem, refused with `507` when it does not.

The declared length is a valid bound in **both** modes, which is the small fact that makes one check enough — a tar is never smaller than the sum of the files inside it, so the request's own length is an upper bound on the bytes about to land. A chunked upload declares nothing and proceeds unchecked, and a filesystem that cannot be measured proceeds too: `statfs` answering null means *do not know*, and a precheck that refused on it would be worse than the `ENOSPC` it is only ever an earlier, cheaper version of.

## Alternatives considered

- **Chunked file frames on the core link (rejected, D1).** No new surface, no new auth, reuses the reconnect logic. Rejected on head-of-line blocking: it makes every terminal on a Core stutter for the duration of an unrelated file copy, and the base64 tax is 33% of a multi-gigabyte transfer. The reconnect logic it reuses is also the wrong reconnect logic — a dropped upload wants a range request, not an event-cursor replay.
- **A second WebSocket, for bytes only (rejected, D1/D2).** Keeps the frames off the control socket and preserves binary framing. Rejected because it is a second connection to authenticate, reconnect and reason about, and because it gets no benefit HTTP does not already give: an upload is a request/response with a body, which is what HTTP is. It would also break [ADR 0024 D1](0024-a-core-serves-many-clients-one-holds-a-sessions-write-lock.md)'s one-link-per-client shape for no gain.
- **A separate HTTPS listener on its own port (rejected, D2).** Cleanly separated, independently restartable. Rejected on the operator: a second port is a second firewall rule, a second proxy entry, and a second thing that can be down alone. Every already-issued registration blob would be missing the field naming it.
- **Plain HTTP behind the operator's own TLS termination (rejected, D3).** Simpler for a Core behind a reverse proxy. Rejected because the client certificate *is* the Core's authentication ([ADR 0002](0002-core-link-auth-and-transport.md)) — terminating TLS elsewhere discards it, and what is left is a bearer over a hop this project does not control.
- **mTLS only, no bearer, since the routes are behind the client cert anyway (rejected, D3).** Rejected because certificate rotation and bearer reissue are different operations on different clocks. The bearer is what expires, and the file surface would otherwise be the one door that stays open after a pairing is revoked.
- **Move `CORE_LINK_PROTOCOL_VERSION` because a new public surface appeared (rejected, D4).** Defensible on the face of it: a new externally consumable surface is a minor under [ADR 0023 D31](0023-release-trains-and-digest-promotion.md), and this train is a minor for exactly that reason. Rejected because the version is a claim about *what two processes speak on this socket*, and nothing on this socket changed. Bumping it would mark every Core in every fleet needs-update over routes on a different protocol they are free never to call. The package minor and the protocol version are answering different questions, and this is the case that shows they are.
- **Buffer a folder download to produce a manifest alongside it (rejected, D5).** Would make the read direction symmetric with the write direction. Rejected because it requires either holding the archive to hash it — unbounded memory or a temp copy of a `node_modules` — or a second traversal, which is the second pass over every byte [ADR 0027 D4](0027-the-filesystem-is-the-model.md) exists to avoid.
- **Queue the second write instead of refusing it (rejected, D6).** Rejected as false kindness: an unbounded silent wait, then two intentions interleaved over one tree.

## Consequences

- **The Core has a second HTTP surface.** `docs/external-api.md` said the hook receiver was the only one; it is amended in this change. The hook receiver stays a separate loopback listener and is untouched.
- **`packages/core` gains no dependency for it.** Raw `node:http` handlers and `URL` dispatch, the same shape `harness-hook-receiver.ts` already uses. No framework enters the Core bundle for three routes.
- **`CoreConnection.httpsBaseUrl` is now read by something.** It was added in phase 2 against exactly this, with a comment saying nothing read it yet. That is no longer true, and the field never had to change shape.
- **The loopback `ws://` Core gets the routes too, over plain HTTP**, and only when a files port is wired. Its core link is already unauthenticated and already spawns VM Shell Sessions, so this adds no exposure — but it is an explicit branch in the server factory rather than an accident, and a loopback Core without a files port keeps exactly the listener it had.
- **A refused-because-busy upload can be refused before its body is sent**, when the client sends `Expect: 100-continue`. The Core registers a `checkContinue` listener, which is what stops Node auto-answering `100 Continue` — a client that does not ask still gets the same 409, only later and after wasting bandwidth.
- **A mid-transfer failure leaves partial results on disk.** A multi-gigabyte tar cannot be staged and swapped, so this surface does not promise atomicity, and the tests assert the honest behaviour rather than an aspiration. What is promised is that the *escape* never happens (ADR 0029), which is a different claim and the one that matters.
- **The SDK gains `canUseFileRoutes()` and `filesCapability()` and nothing else.** `project.files.*` is issue [#166](https://github.com/actana/control/issues/166); this ticket adds only the capability a client needs to know whether to offer it.
