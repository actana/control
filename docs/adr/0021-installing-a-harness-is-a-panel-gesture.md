# Installing a Harness is a Panel gesture, answered on the event log

CLI availability has been Core-published state since issue 11: the Core owns the machine, probes its own PATH, and publishes what it finds (ADR 0010). That made the Panel honest about a missing Harness and completely powerless about it — the "Start a new session" picker greyed the row out, said "CLI not found on PATH", and left the operator to go find a shell on another machine. This ADR records the trigger that closes that gap, because it changes the wire contract and lets a Panel gesture start a long-running process on a Core.

**The Panel asks; the Core installs.** A new `harnessInstall` request frame names one Harness. The Core runs exactly what `actana harnesses install <id>` runs — `installAgentsNow`, the non-interactive path, already written for a machine with no terminal — and then re-probes so the availability event that follows is the operator's answer. Nothing about probing or publishing changes: this adds a trigger, not a second source of truth.

**The outcome travels on the event log, not on the request.** The panel link's per-request timeout is fixed at 30s per client and is not overridable per request, and a vendor installer routinely runs for minutes. A response frame held open for the install's duration would therefore reject a *healthy* install, and would tie the outcome to one browser tab's pending promise. So the Core acks the frame the moment it has validated the id and started the work, and the request is finished there. Success arrives as the ordinary `agents:availabilityChanged` event flipping the Harness to `available`; a definitive failure arrives as a new `harness:installFailed` event carrying an operator-facing message. Both outlive the request itself, a Panel reload, and a link drop mid-install — none of which a pending promise does. Success reaches every tab watching that Core; a failure is acted on by the tabs still waiting on that install, because the tail replays and a failure nobody is waiting for is history rather than news.

**Success is "the probe finds it", not "the installer exited 0".** A vendor installer that exits 0 while leaving nothing on this Core's PATH is a failure the operator has to hear about; the Core reports it as one rather than leaving a Panel row waiting for an availability change that is never coming.

**No failure is ever cached.** The failure message is an event, and on the Panel it lives in the pending-install store — never in the availability map, and never past the next availability snapshot for that Harness. An availability entry is a fact about PATH that the next probe overwrites; an error cached there would outlive its own truth and permanently disable a Harness that is fine. A link drop mid-install is not a verdict either: availability re-hydrates on reconnect and the two terminal conditions above still decide.

**`installing` spans the lifecycle, and lives outside React.** From the click until the Harness is actually available, keyed by Core id *and* Harness id at module scope beside the availability stores. It has to outlive the dialog closing and reopening, a component remount, and a panel-link reconnect. Availability entering `checking` (which the post-install re-probe legitimately does) or republishing an unchanged `missing` is the install still running, and clears nothing.

**`CORE_LINK_PROTOCOL_VERSION` → 0.14.0.** `harnessInstall`, `harnessInstallAck`, and the `harness:installFailed` event kind. The minor moved, so a Core still speaking 0.13.0 is incompatible under the major.minor rule and renders as "needs update" (ADR 0005) rather than a Core that accepts the frame and silently drops it.

## Considered Options

- **Await the install on the request frame (rejected).** The obvious shape, and it needs no new event kind. It cannot work against a fixed 30s request timeout: the common case — a vendor installer taking two minutes — rejects the promise while the install is running healthily, and the operator is told it failed. Raising the timeout for one frame type would mean a per-request timeout the client does not have, and would still lose the outcome on a reload.
- **Poll availability from the Panel and infer the outcome (rejected).** No new event kind, and the success path already works that way. It has no failure signal at all: an install that failed and an install still running look identical, so the row either spins forever or gives up on a timer that is wrong for every installer.
- **Cache the failure in the availability map (rejected).** It would ride the existing event and need nothing new. It inverts the map's meaning: availability is what the probe found, and a failure written there survives every subsequent probe of a Harness that may since have been installed by hand. That is precisely the permanently-disabled row this feature exists to remove.
- **Keep the pending-install state in the dialog's component state (rejected).** Simpler, and it is where a first draft would put it. It dies on the dialog closing, on a remount, and on a reconnect — three things that happen routinely during a two-minute install.
- **Stream the vendor installer's output into the dialog (deferred).** Genuinely better feedback than "Installing...". It needs an output channel, a place to put a scrollback in the picker, and a decision about interactive installers; the Core's non-interactive path is what exists today. Out of scope here, not rejected.
- **Offer install from the `outdated` state too (rejected here).** Re-running a vendor's *installer* over a working install is a more destructive act than what the operator was offered, and every Harness already has an updater and an update-required flow. Unchanged by this ADR.

## Consequences

- **A Panel gesture can now start a long-running process on a Core.** It is bounded: one Harness per request, only ids the shared registry marks offerable, and a second request for a Harness already installing joins the first rather than starting a competing installer over the same files. It is still a real widening of what a connected Panel can cause, and the core-link's mTLS + bearer auth is what stands between it and anyone else.
- **The install runs with no TTY and its output goes to the Core's log.** `installAgentsNow` was written for exactly this (`interactive: false`); the operator watching the Panel sees a row and, on failure, a sentence.
- **Every Core must be updated alongside the Panel** — the minor moved. A Core on 0.13.0 renders as "needs update" rather than dropping the frame silently.
- **Registry-disabled Harnesses ("Coming soon") are untouched.** They probe as `missing` too, and are excluded from `offerableHarnessIds()` on the Core and from the Install affordance in the picker: installing something the probe will never report on would produce a CLI that is installed and permanently invisible.
- **A replayed failure is dropped rather than painted.** The Panel acts on `harness:installFailed` only where it is still waiting on that install. The event tail replays to a tab that opens later, and a message shown to someone who never clicked Install — on a Harness that stays missing, so no later availability change clears it — is worse than silence.
- **The Providers settings page still tells the operator to run the command themselves.** Only the picker grew this affordance; a second surface is a separate decision.
