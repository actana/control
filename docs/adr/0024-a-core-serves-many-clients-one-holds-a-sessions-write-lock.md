# A Core serves many clients, and one connection holds a Session's write lock

A Core accepted exactly one core-link connection. `PtyCoreLinkServer.onConnection` closed whatever socket was there before accepting a new one, and that was the correct shape for a system with one client. #129 gives it three — the Panel, the CLI, and SDK automations — and already listed the consequence under its own known risks: every new client competes with the Panel for the one connection, and `attach` holds it for as long as it is open. Flagged there, solved here. #129 phase 2 defers `session attach` to last for exactly this reason: on a single-connection Core, attaching from the CLI evicts the operator's Panel.

The replacement is **not** many writers. A PTY is a byte stream with no notion of who typed; two clients writing to one harness interleave into nonsense, and an automation driving a session cannot tolerate a stray keystroke from a Panel tab left open in another window. So: **a Core serves many clients at once, and every Session has many Readers and at most one writer.**

The twelve decisions below were settled in a design session and are recorded here so no ticket re-litigates them. Each carries a **D** number that its ticket cites. A ticket that needs one changed amends this record rather than settling it in a comment.

## The decisions

**D1 — A Core accepts many concurrent core-link connections.** The evict-on-connect branch goes. Each connection gets its own event cursor, subscription set and heartbeat — already how `ActiveConnection` is shaped; it was simply only ever instantiated once.

**D2 — PTY output fans out per connection, by subscription.** `PtyCore.setEmitTarget` is a single global callback, so every PTY's `data` goes to the one socket. It becomes a registry, and a connection receives a PTY's stream only after asking for it. A CLI attached to one session must not receive every other session's output on the machine, continuously. Catch-up needs nothing new: `replay { ptyId, sinceSeq }` exists and `data` frames already carry `seq`.

**D3 — The unit of write authority is the core-link connection.** Not a per-client credential, not a logical actor above the socket. There is exactly one Operator per Panel, so the parties that genuinely contend are *programs* — Panel, CLI, SDK automation — and each is exactly one connection. Two browser tabs are one human with two tabs; which of them drives is the Panel's own business, settled between Panel sessions inside the Panel, and never crosses the wire.

**D4 — The lock is scoped to one Session and covers every mutation on it.** Not just `write`: `kill`, and every task mutation addressed at that Session. An automation whose session can be killed by an observer does not hold a lock in any useful sense. Deliberately *not* Core-wide — that would stop the Panel creating a project while a CLI runs a session, which is the ordinary case, not the contended one. Different Sessions on one Core may be held by different clients.

**D5 — A Session starts unlocked, and its creator gets no privilege.** Auto-claiming on create makes "who owns this" depend on history the Core would have to keep, and leaves a Session nobody can claim when its creator exits. Unlocked is a real state; any connection may claim an unlocked Session.

**D6 — Claiming is explicit.** A `claim` frame; a mutation without the lock is an error, never an implicit acquisition.

**D7 — A lock ends on explicit release, on connection drop, or on force takeover. No idle timeout.** A long agent run is *idle by definition* — no mutations for many minutes is the success case — so an idle timeout would drop the lock exactly when losing it costs most. Force takeover exists because otherwise a hung client renders a Session unusable until its process dies.

**D8 — Lock state is published, not discovered by failing.** It rides the Session snapshot and emits an event on every change. A read-only Panel tab must render the terminal non-editable *before* a keystroke, `actana session ls` must show it, and the loser of a force takeover must learn it when it happens rather than on its next write.

**D9 — A connection presents a stable client id, used only for reaping.** Not for authority, not verified. With D1 the old evict-on-reconnect no longer runs, so a reloaded Panel tab leaves a socket alive for up to `HEARTBEAT_TIMEOUT_MS` (45s) still holding locks. A reconnecting connection presenting the same client id replaces its predecessor and inherits its locks.

**D10 — The write lock is a coordination mechanism, not a security boundary.** The Core's only authentication is the bearer in the registration blob, and anyone holding it can open a VM Shell Session and `kill` the process directly. A lock defended against someone with a shell on the machine is theatre. This is the posture #129's F3 takes for path confinement: an accident guard, stated as one. Per-client credentials with revocation would be a separate effort with its own ADR, and are not a prerequisite for anything above.

**D11 — `CORE_LINK_PROTOCOL_VERSION` does not move; the capability is announced on `ready`.** `ready` carries an optional `multiConnection: { version: 1 }`; absent means the old single-connection Core. A new client against an old Core sees no capability and behaves as today; an old client against a new Core works untouched — it never claims, and never notices it is no longer evicting anybody. Moving the minor would mark every Core in every fleet needs-update for a capability most will never exercise.

**D12 — Locks live in memory and die with the Core.** Not persisted, because the PTYs they guard do not survive the daemon either. A Core restart returns every Session to unlocked, which is the correct state for a Session with no running process behind it.

## Considered Options

- **Many writers to one Session, with no lock at all (rejected).** The smallest change — remove the eviction branch and stop there. Rejected because a PTY has no notion of who typed: two clients writing to one harness interleave into a stream neither of them meant, and the failure is silent and unattributable. Read concurrency is what operators actually ask for; write concurrency is what nobody can use.
- **A per-client credential, or a logical actor above the socket, as the unit of write authority (rejected, D3).** It sounds more principled and it buys nothing here: there is exactly one Operator per Panel, so the parties that contend are programs, and a program is exactly one connection. It would also make authority something the Core has to store, verify and revoke — see D10 for why that is a different effort.
- **The creator of a Session holds it automatically (rejected, D5).** Convenient for the common case and wrong in the case that matters: it makes ownership depend on history the Core would have to keep, and a Session whose creator exited would be locked by nobody with no way to claim it.
- **First mutation claims the lock implicitly (rejected, D6).** Saves a frame and defeats the purpose. With D5 in force nothing else guards a running automation, so one keystroke in a Panel tab left open in another window would take the Session out from under it — the exact failure this ADR exists to prevent.
- **An idle timeout on the lock (rejected, D7).** The usual liveness answer, and this is the one domain where it inverts: a long agent run is idle by definition, so the timeout fires precisely on the healthy long-running case it would hurt most. Connection drop and force takeover cover the two real failures without it.
- **Moving `CORE_LINK_PROTOCOL_VERSION` instead of announcing a capability on `ready` (rejected, D11).** Version-locking is this project's default and it is the wrong instrument here: the minor moving marks every Core in every fleet "needs update" over a capability most of them will never exercise, and the honest alternative — a capability whose absence yields exactly today's behaviour — costs one optional field.

## The rule this amends

`CONTEXT.md`'s Rules said the Panel and its Cores are version-locked — *"never a degraded or feature-detected mode"*. D11 is feature detection, and so is #129's F9 for the files surface, so the rule needed amending either way.

**Narrowed, not deleted:** an additive surface may announce itself on `ready` **only where its absence yields today's behaviour exactly**, not a lesser one. `multiConnection` absent means single-connection eviction, which is precisely today. A capability that changes what an existing frame means is not additive and still moves the version.

Two more Rules changes ride with it: `One Core link per Core, multiplexed` is restated as **per Core client**, and a new rule is added — **many Readers, one writer, per Session**. Four domain terms land alongside: **Core client**, **Core alias**, **Session lock**, **Reader**. Banned as synonyms: session owner, mutex, reservation, observer, spectator, participant, client session.

## Consequences

- **The Core gains contention it has never had.** Nothing in `PtyCore` expected two callers. The lock table, the subscription registry and the emit fan-out are all new shared state in a process whose assumptions have been effectively single-threaded. #129 flags the same class of risk for concurrent HTTP against a live WebSocket; the mitigations should be written once.
- **Force takeover is unrecoverable by design.** The loser's in-flight keystrokes are gone. D8 makes it visible; nothing makes it undoable.
- **The claim race is real and accepted.** D5 leaves a window between session start and first claim in which any client can take it. An automation must claim immediately after starting.
- **No cap on connection count is specified.** A Core with a runaway client reconnecting in a loop accumulates sockets until the heartbeat reaps them.
- **Reconnect defects stop hiding.** Evict-on-connect made a fresh socket always win, so a failed reconnect was indistinguishable from a successful one. Without it, a stale connection holds its Session locks while the heartbeat waits out its 45 seconds — which is why #139 is a hard blocker for this effort rather than a neighbour of it.
- **VM Shell Sessions are assumed to follow the same rule** as harness Sessions. Not separately decided — the first ticket that touches one should confirm or amend D4.
- **The decisions land across five steps, not one.** D1 and D12 shipped with this record (#141): the connection registry, and locks that never outlive the process because there are none yet to persist. D2 landed with #142 — the interim fan-out that gave every registered connection every PTY's output is gone, and a connection is served a PTY only after a `ptySubscribe` for it. D11 is #143. D3–D7 and D10 landed with #144: the `claim` / `release` / `forceTakeover` frames, the Core-wide lock table keyed by Session, and the gate on `write`, `kill`, every `tasksMutate` addressed at a Session, `harnessPrompt`, and `spawn` against a Session that already exists. D8 landed with #145: the lock on every Session snapshot and the `session:lockChanged` event. D9 landed with #146: the `reclaim` frame and the transfer that moves a reconnecting client's locks in place. The Panel's half of D3 and D8 landed last with #147, which is where all of it is finally seen: a Session another client holds renders read-only in the same terminal component with its input taken away, a claim and a confirmed force takeover are offered, and the Panel arbitrates between its own tabs.

- **The Panel's tab arbitration is a second name, not a second lock** (#147, D3). The Panel is one Core client and holds a Session's lock once for all of its browser tabs, so the lock cannot answer which tab drives — two tabs of one Panel are told the identical `held-by-you`, and both would write. That arbitration is the **Session drive** (`CONTEXT.md`): Panel-scoped, settled in the panel-link router between Panel sessions, with no core-link frame, no event-log row and nothing a Core hears about, exactly as D3 says. Naming it separately is the decision, not an accident of implementation: a Session **held** by another client and a Session **driven** in another tab are read-only for unrelated reasons, are escaped by unrelated gestures — a force takeover across the wire, against a keyboard moved inside one Panel — and their losers are told different sentences, because one lost their unsent keystrokes and the other lost nothing at all. Collapsing them would make every "it went read-only" report ambiguous between a contended Session and a second tab the operator forgot was open.
- **The Panel derives its own lock state rather than refetching it** (#147, D8). The published `lock` on any snapshot seeds it, the `session:lockChanged` events move it, this connection's own claim / release / takeover answers settle what it asked for, and `reclaimResult.taskIds` restores it after a reconnect — so a claim reflects on screen without a refetch, which is what D8 exists to make possible. The one subtlety is that the Core answers the frame and appends the event, and the Panel sees both: because live events are polled, its *own* takeover's `taken-over` row arrives after the answer, and read naively it would tell the tab that just took a Session that somebody had taken it away. The register suppresses exactly one echo per gesture it performed, and a snapshot deliberately does not clear that suppression — a list landing in between would leave the echo to be read as another client's claim.
- **The published lock is addressed, not broadcast** (#145, D8). The `lock` on a Session snapshot is stamped for the connection the snapshot is being sent to — `{ writable, state }`, where `state` is `unlocked`, `held-by-you` or `held-by-another` — so two clients listing the same Session are told different things about it, and neither compares a holder against itself. `held-by-another` is the whole of what a watcher learns about a holder that is not itself: no client id, no connection id, nothing correlatable. That is D3 and D10 held to on the wire — the holder is a connection, the lock is coordination rather than security, and an identity published to every watcher would be a fact about who is working where that nothing in this effort needs. `writable` is carried alongside `state` rather than derived by each client, because *which states are writable* is a Core-side rule: an unlocked Session is writable by anybody, which is D11's compatibility promise rather than a property of the word.
- **A dedicated event kind, on the `project:appearanceChanged` precedent** (#145, D8). `session:lockChanged` fires on claim, on release — including the release a connection drop performs — and on takeover, carrying `{ taskId, transition, locked }` and no identity. Widening `task:updated` to carry lock state was rejected for the reason ADR 0017 and ADR 0022 both give: the frame stops documenting what changed, every client refetches on everything, and a reconnecting client replaying a tail cannot tell a takeover it must react to from a title edit it can ignore. The event says *that* the lock moved and the snapshot says what that means for the asker, because one logged row is read by every connection and the answer differs per connection. It is an ordinary event-log row, so it replays by cursor like every other one.
- **Nothing changed publishes nothing** (#145). An idempotent re-claim by the holder, a denied claim, a release from a connection that holds nothing, and a takeover by the current holder all answer their frame and append no event — an event for any of them would be a transition nobody made, and watchers would act on it.
- **The published surface rides the capability, and the version does not move** (#145, D11). The `lock` field is optional and a Core that does not announce `multiConnection` omits it and appends no lock events; absent reads as "this Core has no lock table", which is exactly the single-connection Core that shipped before it. Issue 84 bumped the minor for snapshot fields and this does not, because there the absence yielded something *lesser* than today — a Panel synthesizing `titleManuallySet: false` rendered a Session its generator could rename out from under the operator — while a Panel that predates `lock` renders exactly what it renders today.
- **A refusal and a vanished Session are different frames, deliberately** (#144). A mutation aimed at a Session another connection holds comes back as an `error` carrying the code `session-locked`; a mutation aimed at a Session this Core no longer has comes back as the ordinary `writeResult { ok: false }` / `killResult { ok: false }` / `tasksMutateResult { task: null }` it always did. A client has to be able to tell them apart without reading prose, because one of the two is worth retrying after a claim and the other never is. The optional `code` on the `error` frame is the whole of the new vocabulary; it is absent on every error that shipped before it.
- **An unlocked Session is writable by anybody, and that is what D11 buys.** The gate refuses a mutation only when *another* connection holds the Session. D6's "a mutation without the lock is an error" governs acquisition — a mutation never becomes a claim — not the unclaimed case: a client that never claims, which is every client that predates this, has to keep working exactly as it does today, or the capability's absence would yield something lesser than today rather than precisely it. That is also why the claim race in the known risks above is real rather than theoretical.
- **`harnessPrompt` is gated, because of where it lands** (#144). The frame reads like telemetry — the Panel reporting a prompt it scraped off the terminal because the harness's hooks will not — but it reaches the title generator, which writes the task row's title through the same writer a gated `tasksMutate` uses. D4's "every task mutation addressed at that Session" is decided by where a frame lands, not by how it reads, so it is gated with the rest. Small in consequence, since the generator leaves a real or operator-set title alone; the enumeration is complete either way.
- **`spawn` is gated on the `taskId` it names** (#144), though D4 does not enumerate it. A `spawn` against a Session another connection holds starts a *second* process on the Session that connection is driving — two harnesses in one worktree, which is a worse outcome than the stray keystroke the lock was written for and the same kind of interference. The `resize` reading does not transfer: a Reader has a real use for a resize and none for a spawn it may not then type into, because the lock is keyed by `taskId` for every PTY kind, so the first `write` to the new PTY would come back `session-locked` anyway. A refusal at the spawn is that same answer, one round trip earlier. D5's window is untouched — a Session nobody holds is spawned for anybody, so a creator still spawns without claiming.
- **The client id reaps, and it is the transfer's atomicity that carries D9** (#146). A connection presents its id on a `reclaim` frame; the Core closes whatever connection last presented that string and moves its Session locks across. The locks are rewritten in place, in one sweep, *before* the predecessor's socket is touched — because dropping a connection releases every lock it holds, so the other order leaves those Sessions unlocked, and an unlocked Session is writable by anybody (D5, D11). That gap is the whole defect the frame exists to close; reaching the same end state through release-then-reclaim would not be a smaller version of this decision but the absence of it. The heartbeat is untouched and still reaps the client that never comes back — the reclaim is the answer for the one that does, in a round trip rather than in 45 seconds.
- **The client id is not verified, and nothing may start verifying it** (#146, D9 with D10). It is a string a client made up. It is refused before `auth` like every other frame, so it never authenticates and never substitutes for the bearer; and the only thing it can move is authority any authenticated connection can already take unconditionally with `forceTakeover`, so presenting somebody else's id is a slower spelling of a frame that is already unconditional rather than an escalation. The reviewer's question — how do we stop a client claiming another's id — has D10's answer: whoever opened the socket holds the bearer, and a bearer holder can open a VM Shell Session and kill the process. Signing it would defend nothing and would build the per-client credential D3 rejected by the back door.
- **Where the id comes from is per Core client, and never the registration blob** (#146, D9). The blob is machine-scoped, so an id derived from it — a `coreId`, a bearer digest — would make the Panel, the CLI and every automation on that machine a single connection, each reconnect reaping the others: the exact opposite of D1. The Panel mints one per link it terminates and holds it for the life of that link, which is what a reconnect needs; the ghost it reclaims is a socket whose peer never sent a FIN, which leaves the Panel process running and reconnecting with the id it has held all along. A Panel that has genuinely restarted is a new Core client, and the sockets of the process it replaced were closed by its kernel as it died. The CLI mints one per invocation.
- **A durable id would have two live Panel processes reap each other, and nothing would stop them** (#146, D9). The argument above is about a process that has died; the sharper one is about two that are alive. Were the id persisted and shared — a rolling restart with the old container still draining, two replicas of the service over one registry — both processes would present the same string, and each connect would close the other's socket and take its Session locks, an alternating handover that never settles and leaves the operator's keystrokes landing on whichever process dialled last. That is the registration blob's failure by another route, and the reason it is not merely theoretical is that the durable store is already in place: the Core registry holds one replay cursor per Core and the client persists through it (`core-link-manager.ts`), so "it would need a registry column" understates how available that option is. Per-instance ids make the case unrepresentable — each process mints its own, so two concurrent Panels coexist exactly as the Panel and the CLI do (D1), and an id only ever matches the connection its own process left behind. The Core still does nothing to detect two connections presenting one id, because the posture is D9's throughout: reaping is coordination between a client and its own predecessor, so a shared id is an accident of misconfiguration to be diagnosed and corrected in the deployment, not an attack the Core defends against — and the reaper could take those Sessions with `forceTakeover` anyway. If a durable id is ever taken up, it is this concurrency, not the reconnect, that its ticket has to answer first.
- **`resize` is not gated** (#144). D4 names the mutations the lock covers — `write`, `kill`, and every task mutation addressed at the Session — and a resize is none of them: it is how a client tells the PTY the size of the viewport it is painting into, and a Reader has one of those too. A Reader whose resize were refused would render the Session reflowed to somebody else's terminal, which is a worse outcome than the interference gating it would prevent. Widening D4 to cover it is an amendment to this record, not a call for an implementing ticket.
- **Subscribing and catching up are ordered, not merely both done (D2).** Between a subscription taking effect and the client's `replay` being served, the PTY keeps emitting. The Core holds that output for a subscription that asked to catch up, serves the replay from the client's own `sinceSeq`, then drains what it held past that window — so live bytes never land in front of the scrollback they follow. A PTY that exits inside that window has its exit held and drained too: nothing will emit a second one, and a subscriber that never learns of it waits forever on a dead process. The alternative — replay first, then subscribe — loses whatever is emitted in between, which is worse than mis-ordering it.
- **A connection is subscribed to what it spawned.** The id does not exist until the `spawned` answer, so nothing else can ask in time, and a harness's first lines would be lost to the round trip. Any other connection still has to ask.
