# A Core serves many clients, and one connection holds a Session's write lock

A Core accepts exactly one core-link connection. `PtyCoreLinkServer.onConnection` closes whatever socket was there before accepting a new one (`packages/core/src/pty-core-link-server.ts`), and the comment explains why it was written that way: a Panel renderer reload should not leave a dead socket behind. That is the correct behaviour for a system with exactly one client, and the system has had exactly one client.

It stops being correct the moment there are three. #129 puts an SDK and a CLI on the same core link as the Panel, and lists the consequence under its own known risks — *"every new client competes with the Panel for it; `attach` holds it for as long as it is open. Flagged, not solved here."* Phase 2 defers `session attach` to last for exactly this reason: today, attaching from the CLI evicts the operator's Panel.

This ADR removes the eviction and says what replaces it.

The replacement is not "many writers". A PTY is a byte stream with no notion of who typed; two clients writing to one harness interleave into nonsense, and an automation driving a session cannot tolerate a stray keystroke from a Panel tab someone left open. So: **many readers, one writer, per Session** — and the writer is named by the connection.

## Decisions

**D1 — A Core accepts many concurrent core-link connections.** The evict-on-connect branch goes. Each connection gets its own event cursor, its own subscription set, and its own heartbeat, which is already how `ActiveConnection` is shaped — it was simply only ever instantiated once.

**D2 — PTY output fans out per connection, by subscription.** `PtyCore.setEmitTarget` is a single global callback today, so every PTY's `data` goes to the one socket. It becomes a registry, and a connection receives a PTY's stream only after asking for it. A CLI attached to one session must not receive every other session's output on the machine, continuously, forever. Catch-up needs nothing new: `replay { ptyId, sinceSeq }` already exists and `data` frames already carry `seq`.

**D3 — The unit of write authority is the core-link connection.** Not a per-client credential, not a logical actor above the socket. There is exactly one Operator per Panel (`CONTEXT.md`), so the actors that genuinely contend are *programs* — Panel, CLI, SDK automation — and each of those is exactly one connection. Two browser tabs are one human with two tabs, and which of them drives is the Panel's business, settled between Panel sessions inside the Panel. Pushing that arbitration onto the wire would put a field on every mutating frame to solve a problem one level up.

**D4 — The lock is scoped to one Session and covers every mutation on it.** Not just `write`: `kill`, and every task mutation addressed at that Session. An automation whose session can be killed by an observer does not hold a lock in any useful sense. It is deliberately *not* Core-wide — a Core-wide lock would stop the Panel creating a project while a CLI runs a session, which is the ordinary case, not the contended one.

**D5 — A Session starts unlocked, and its creator gets no privilege.** Auto-claiming on create would be convenient and is rejected: it makes "who owns this" depend on history the Core would have to keep, and it means a client that starts a session and exits leaves a Session nobody can claim. Unlocked is a real state, and any connection may claim an unlocked Session.

**D6 — Claiming is explicit.** A `claim` frame, and a mutation without the lock is an error rather than an implicit acquisition. The alternative — first mutation takes it — was rejected because, with D5 in force, nothing else guards a running automation: one keystroke in a Panel tab would silently take the session out from under it.

**D7 — A lock ends on explicit release, on connection drop, or on force takeover. There is no idle timeout.** An idle timeout is wrong here specifically: a long agent run is *idle by definition* — no mutations for many minutes is the success case, not the abandoned one — and it would drop the lock exactly when losing it hurts most. Force takeover exists because without it a hung client holding a lock renders a Session unusable until its process dies.

**D8 — Lock state is published, not discovered by failing.** It rides the Session snapshot and emits an event on every change. A read-only Panel tab must render the terminal as non-editable *before* a keystroke, `actana session ls` must show it, and the client that loses a force takeover must learn it when it happens rather than on its next write.

**D9 — A connection presents a stable client id, used only for reaping.** Not for authority and not verified. With D1 the old evict-on-reconnect no longer runs, so a reloaded Panel tab leaves a socket alive for up to `HEARTBEAT_TIMEOUT_MS` (45s) still holding locks. A reconnecting connection presenting the same client id replaces its predecessor and inherits its locks. Forty-five seconds of a ghost holding your session is a daily-frequency event, and the alternative trains operators to reach for force takeover reflexively, which defeats D7's point.

**D10 — The write lock is a coordination mechanism, not a security boundary.** The Core's only authentication is the bearer in the registration blob, and anyone holding it can open a VM Shell Session and `kill` the process directly. A lock defended against someone with a shell on the machine is theatre. This follows the same posture #129's F3 takes for path confinement: an accident guard, stated as one. If per-client credentials with revocation are ever wanted, that is a separate effort with its own ADR, and it is not a prerequisite for any of the above.

**D11 — `CORE_LINK_PROTOCOL_VERSION` does not move; the capability is announced on `ready`.** `ready` carries an optional `multiConnection: { version: 1 }`; absent means the old single-connection Core. A new client against an old Core sees no capability and behaves as today. An old client against a new Core works untouched — it simply never claims, and never notices that it is no longer evicting anybody. Moving the minor would mark **every Core in every fleet** needs-update for a capability most of them will not exercise. This is the same mechanism #129's F9 chose for the files surface, and it **amends the version-lock rule in `CONTEXT.md`** — see Consequences.

**D12 — This lands as its own release train, between #129 phases 1 and 2.** It is not extraction: phase 1's success test is *"the Panel behaves identically"*, and this changes Core semantics, so folding it in muddies the hard binary test D14 of #129 exists to protect. It must precede phase 2, because phase 2 ships `session attach`, and shipping attach on a single-connection Core means shipping a command that evicts the operator's Panel.

## Considered Options

- **Leave the single connection and let clients take turns (rejected).** Costs nothing to build. Rejected because "taking turns" is what eviction already is, and it means the CLI cannot be used while the Panel is open — which describes every real working session.
- **Lock per Core rather than per Session (rejected).** Simpler: one flag, one holder. Rejected because it conflates contention with presence. The overwhelmingly common case is two clients working on *different* Sessions of the same Core, and a Core-wide lock makes that the forbidden case.
- **A logical actor above the connection, so each browser tab is its own writer (rejected).** Genuinely better if two humans shared a Panel. They do not: `CONTEXT.md` puts exactly one Operator on a Panel, created at first boot. Adopting it would put an actor id on every mutating frame — a field the SDK owns and therefore expensive to remove after publication — to arbitrate between one person's own tabs. If multi-human Panels are ever built, this is the decision to revisit, and D3 is where to start.
- **Per-client credentials, so the lock is enforceable (rejected).** It would make "who may write" verifiable and allow revoking one CLI without re-pairing everything. Rejected as a credential-issuance product — minting, rotation, revocation, storage, a UI — bought for an adversary who already has a shell (D10).
- **First mutation claims an unlocked Session (rejected).** No round-trip in the common case. Rejected under D5: with no creator privilege, an automation would be unprotected for its whole run.
- **Bumping `CORE_LINK_PROTOCOL_VERSION` to 0.16.0 (rejected).** The honest reading of the existing version-lock rule, and it needs no new mechanism. Rejected because it marks every Core in every fleet as needs-update to buy a capability that a fleet with one Panel and no CLI will never use — and it makes upgrading the Panel a fleet-wide maintenance event rather than a Panel deploy.

## Consequences

- **The version-lock rule in `CONTEXT.md` is narrowed, and this is the second time.** The rule reads *"never a degraded or feature-detected mode"*, written when every protocol change altered behaviour both sides depended on. D11 is feature detection, and so is #129's F9. The rule is amended to govern *frames that change the meaning of existing behaviour*, while additive surfaces may announce themselves on `ready` and be absent. This is a real weakening, and the guard against it becoming a general escape hatch is that a capability may only be announced when its absence yields the **current** behaviour, unchanged — not a lesser one. `multiConnection` absent means single-connection eviction, which is exactly today.
- **`session attach` becomes buildable, and #129's known risk is closed.** Phase 2's ordering constraint — attach last, because it holds the Core's only connection — is removed. The map issue's risk entry should be struck rather than left to read as open.
- **Reconnect stops being papered over.** Evict-on-connect currently hides every reconnect defect: a fresh socket always wins, so a failed reconnect looks like a successful one. Under D1 a stale connection persists until the heartbeat kills it and, under D7, holds its locks while it does. **The overnight session-detach defect must be diagnosed before this lands** — it is filed separately and is a blocker on this train, not a follow-up.
- **The Core gains contention it has never had.** Nothing in `PtyCore` currently expects two callers. The lock table, the subscription registry, and the emit fan-out are all new shared state on a process that has been effectively single-threaded in its assumptions. #129 flags the same class of risk for concurrent HTTP against a live WebSocket; the mitigations are the same and should be written once.
- **Locks live in memory and die with the Core.** They are not persisted, because the PTYs they guard do not survive the daemon either. A Core restart returns every Session to unlocked, which is the correct state for a Session with no running process behind it.
- **A Core alias stays a per-Panel nickname.** Two Panels on one Core may call it different things, and the CLI's `~/.config/actana/cores/<name>.txt` name (#129 D9) is a third, unrelated name. This is deliberate — see #19 — and follows the same split ADR 0022 drew between Core facts and Panel-side presentation.
- **`CONTEXT.md` gains **Session lock**, **Reader**, and **Core alias**,** and the rule *"One Core link per Core, multiplexed"* is restated: still one link per Core *per client*, no longer one link per Core.
