# Singular Panel UI across Loopback and remote Cores

The Panel renders every Core through the same components — `ProjectBar`, `SessionGrid`, `NewAgentDialog`, `TerminalPane`, notification surface — with `coreId` threaded through as a parameter. Loopback is not a special case in the UI; it is a Core with an in-process transport. Every affordance available for a local Session (icon, pin, availability check, rename, status states, notifications) is available for a remote Session by construction, because there is only one code path. The Fleet view is reduced to a strict aggregate; the Per-Core work surface is the same shell you see for a Loopback Core.

## Considered Options

- **Unify (chosen).** One shell, `coreId`-parameterized. Transport branches live inside the API layer (`api.createTask(coreId, …)`, `useCliAvailability(coreId)`) and inside `TerminalPane` (which already routes on `descriptor.coreId` since issue 07). `NewAgentDialog` accepts a `coreId` prop and its availability check reads from a per-Core store fed by the Harness's own probe. Task/Project metadata mutations (pin, rename, icon) flow through a shared core-link mutation surface — Loopback executes them in-process, remote Cores over the WebSocket. `FleetView` retains only the aggregate dashboard; its previous embedded per-Core drill (`CoreProjects`, `CoreProjectTasks`, `TaskRowMini`, `NewTaskDialog`) is deleted, and clicking a Core card navigates into the standard shell route scoped to that Core.
- **Port / duplicate (rejected).** Keep `FleetView`'s bespoke rows and its `NewTaskDialog`, and copy affordances into them one by one (add SessionIcon to `FleetTaskRow`; add a pin toggle; graft availability checks into `NewTaskDialog`; …). Rejected because every future Session-level affordance would need to ship twice — once in the Loopback code path and once in the Fleet code path — and history says the two would drift the moment one side landed a feature the other did not. The whole reason parity is missing today is that this path was taken for issues 05–07 and the Fleet UI accreted its own shape.

## Consequences

- `SessionGrid`, `ProjectBar`, and `NewAgentDialog` gain a `coreId` prop; every internal API call fans that `coreId` into the transport layer, where it selects Loopback (in-process) or remote (`electron.fleet.*`) as needed.
- `useCliAvailability` becomes `useCliAvailability(coreId)`; the underlying store is fed by a new field on the core-link state snapshot — the Harness runs the same availability probe it already runs locally and publishes `{agentId → status}` alongside its Task/Project state. Loopback and remote Cores emit the identical snapshot shape.
- Task metadata (pin, rename, icon) becomes Harness-owned. Three new core-link mutation frames (`taskPin`, `taskRename`, `taskSetIcon`) and one project frame (`projectPin`) route through the existing `HarnessMutationPort` established in ADR-0004. Loopback and remote Cores accept them identically; two Panels connected to the same Core see identical pin/icon state.
- `FleetView` is reduced. `CoreProjects`, `CoreProjectTasks`, `TaskRowMini`, `ProjectCardMini`, and `NewTaskDialog` are deleted from `FleetView.tsx`. What remains is the aggregate dashboard (`FleetDashboard`, `FleetTaskRow`, `CorePicker`, unreachable-Core surface). Clicking a Core card navigates out of Fleet view into the standard per-Core shell.
- The shell has no in-shell Core switcher. Switching Cores requires returning to Fleet view. This is a deliberate simplification (see Q5 in the grilling that produced this ADR): projects differ per Core, so a switcher would swap almost every visible element on every use — the navigation gesture through Fleet view is honest about that reset.
- UI-string convention: user-facing labels continue to call a Task a "Session" (per `CONTEXT.md`'s Task entry). Types, function names, DB columns, and core-link frames keep the name `Task`. This is a rendered-string convention only; nothing else moves.
- No back-compat surface. This is the first version of unified remote-Core UI; Panel and Harness ship together and require version match. No feature-detection code paths in the Panel; the Harness always emits the new state shape.
- Rollout is incremental in the detached-core issue series (issues 08+): shell mount first, then metadata mutations (icon, pin), then availability publish + `NewAgentDialog` wiring. Each slice is independently reviewable and reversible; the singular-UI invariant is the target end state, not a big-bang PR.
