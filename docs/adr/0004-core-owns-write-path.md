# Harness process owns the write path against its SQLite

> _Written before the #33 rename. Read "Harness" as what is now a **Core**, and "agent"/"TaskAgent" as what is now a **Harness**; the wording is left as it was decided._

The Harness process opens `missioncontrol.db` read-write and executes project/task mutations directly through pure-SQL helpers, rather than forwarding those mutations over loopback HTTP to a bundled `src/server/` sibling. This mirrors the pattern already established for the read path (`electron/harness-query-store.ts` + `src/shared/harness-query.ts`, issue 07) and for schema bootstrap (`electron/harness-db-bootstrap.ts`, issue 02): the Harness process is the sole VM-side owner of the shared SQLite, so the extra hop through a co-hosted HTTP server would only add moving parts without changing ownership.

## Considered Options

- **Harness writes directly (chosen).** `PtyCoreLinkServer` receives `projectsMutate` / `tasksMutate` / `sessionsList` frames and calls a `HarnessMutationPort` backed by `electron/harness-mutation-store.ts`, which shares a single read-write connection with the same DB the read path already reads. Pure SQL helpers in `src/shared/harness-mutations.ts` are the shape (mirrors `harness-query.ts` for reads). Path validation lives on the Harness — a project's `path` is a VM path (CONTEXT.md), so only the Harness can `fs.statSync` it before accepting the row.
- **Bundle `src/server/` as a sibling VM process, forward writes over loopback HTTP (rejected).** ADR-0001 sketched this ("the bundled server must be extracted from Electron and made to run headless as the Harness process"). Rejected for the write path because (a) the server has ~35 controllers and ~50 services rooted in `~/` alias imports and a Vite bootstrap chain; carving out just projects/tasks/worktrees for a headless build is a large surgery for one ticket, and shipping the whole thing means also shipping code paths (skills, sandboxes, code-graph, provider-usage) that have no meaning on a remote Harness. (b) The read path (issue 07) already committed to "Harness process owns SQLite directly," so keeping writes on a different ownership model would split the store's writers across two processes for no observable benefit — the same DB, the same WAL, the same schema, one process. (c) The mutations we actually need for the write path v1 (create project + rename + archive, create/update task, list sessions) are a small, stable subset of the server's HTTP surface — the pure-SQL restatement is dozens of lines, not the full server.

## Consequences

- The Harness now opens the shared SQLite in three modes across three files: read-only (`harness-query-store.ts`), read-write (`harness-mutation-store.ts`), and appender (`event-log-store.ts`). SQLite WAL tolerates this — the two-writer pattern documented in `event-log-store.ts` extends naturally to a second writer for row mutations.
- The pure-SQL helpers in `src/shared/harness-mutations.ts` are the source of truth for the shape of the mutations the core-link exposes. They must stay compatible with the DDL in `src/db/schema-bootstrap.ts` (the same file `electron/harness-db-bootstrap.ts` calls at boot) — if the loopback server ever adds a required column, both this file AND the DDL move together.
- The Harness appends `project:created` / `project:renamed` / `project:archived` / `task:created` / `task:updated` events (kinds emitted by `PtyCoreLinkServer.recordProjectMutation` / `recordTaskMutation`) to the same monotonic event log the PTY lifecycle events use, so a reconnecting Panel learns about mutations via the existing `subscribe` / `event` / `eventsReplayed` replay path (issue 02). No separate event channel.
- Path validation is the Harness's job — the Panel sends a candidate VM path; the Harness rejects it (`ValidationError`-flavored `error` frame) if not absolute, not resolvable, or a file. The Panel never sees the VM's filesystem.
- The loopback Panel + server flow is untouched — the local server keeps owning writes via the HTTP API. The core-link mutation frames exist for remote Cores (and, incidentally, work on loopback too, but nothing routes them there yet — issues 05/06 land the Panel UX).
- If a future ticket ever does bundle `src/server/` on the Harness, the mutation frames become a no-op passthrough and the pure-SQL helpers can be deleted — the ownership seam is the `HarnessMutationPort` interface, not the SQL itself.
