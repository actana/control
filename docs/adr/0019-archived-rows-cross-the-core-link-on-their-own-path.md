# Archived rows cross the core-link on their own path

The Core's task-listing query selects `WHERE archived = 0`, and has since issue 07. That was deliberate and is documented in the code: the Fleet view is for active work, and the Panel caches nothing, so there was no reason to ship rows nobody would render. The decision was never written into an ADR, which is why this is a new record rather than an amendment — ADR 0004 covers the *write* path and attributes the read path to "issue 07".

The consequence only became visible once archiving a Core-owned Session was routed correctly (#18). The Panel's Archived view derives its contents by filtering the task list it already holds for `archived === true`. For a Core-owned project that list arrives already stripped, so the filter always yields nothing: the Archived tab never appears, the view auto-exits the moment it is entered, and Restore — which existed, and even routed to the wrong place — could not be invoked at all. Archive was a one-way hide. No data was lost; the rows sat on the Core, unreachable from the UI.

**Archived rows get their own request frame.** `archivedTasksList` with an optional `projectId`, answered by `archivedTasksListResult`, backed by a new `queryArchivedTasks` selecting `WHERE archived = 1` alongside the existing `queryTasks` rather than parameterising it. The Panel sends it when the Archived view opens, not on project open. `CORE_LINK_PROTOCOL_VERSION` → 0.12.0.

**The active query is untouched.** `queryTasks` keeps its `WHERE archived = 0` and gains no parameter, no flag, and no path by which an argument could make it return an archived row. This is the whole point of a second frame over a flag on the first: the invariant holds by construction rather than by every future caller remembering not to pass something on the hot path.

**`tasksListResult` gains an unconditional `archivedCount`.** A required integer, carrying no row data. The Panel needs archived *presence and count* continuously while the active view is showing — it gates the Archived tab, labels it, fills the "View archived" tooltip, drives the auto-exit when the list empties, and sizes the delete-confirm dialog — but it needs the *rows* only when that view is open. Those are two different needs with two different shapes, so they travel separately: the count rides an answer already in flight, at the cost of one `COUNT(*)`, and the rows stay lazy and pageable-later.

## Considered Options

- **An `includeArchived` flag on `tasksList` (rejected).** The smallest diff, and the reason it was rejected is not hypothetical: the flag would sit on the Fleet view's hot path, where any future caller passing it — or any refactor defaulting it wrong — silently reinstates the bug this ADR fixes. A second frame cannot be passed by accident.
- **Fetching the archived list alongside the active one on project open, and taking `.length` (rejected).** It needs no contract change beyond the new frame, which is what makes it tempting. But it pulls an unbounded row list on every project open in order to read one number off it, makes archived rows cross the link on the hot path — preserving the invariant literally while defeating it in effect — and forecloses the paging a dedicated read path exists to enable.
- **Accepting that archive is terminal for Core-owned Sessions, and hiding the Archived view for them (rejected).** Honest about the architecture and cheapest to build, but it makes the archive button mean two different things depending on where the Session lives, which the operator has no way to see. ADR 0005 says the same components render every Core's data; a view that exists for one owner and not the other contradicts it.
- **Dropping the count and always showing the Archived tab (rejected).** This would need no scalar at all. Rejected as a product regression: an empty tab on every project, and a "View archived" affordance that leads nowhere, to save one integer on a round trip that was happening anyway.

## Consequences

- **Every Core must be updated alongside the Panel.** The minor moved, so a Core still speaking 0.11.0 is incompatible under the major.minor rule and renders as "needs update" (ADR 0005). That is the honest outcome: `archivedCount` is required precisely so an older Core cannot answer without it and leave the Archived tab silently absent — which is the bug, not a degraded mode.
- **The archived list is a second read path to keep consistent.** Anything that moves a row across the archived line has to refresh both lists. On the Panel that means the archived query is invalidated wherever the task list is — the live core-link event handler, the link-reconnect refetch, and the archive/restore/delete handlers — and it is keyed outside the project's cache tree so no unrelated invalidation sweeps it up.
- **The Panel's archived count lives in its own cache bucket, written by the task-list fetcher.** It arrives on the task-list answer but is consumed by the Archived tab while the active view is showing, so it is parked beside that list rather than widening the list's shape for every reader of it. The bucket has no fetcher of its own; it is refreshed whenever the task list refetches.
- **A Panel-owned project keeps its single read path.** Its task list carries its archived rows already, so both the count and the rows are still a filter away and neither new frame is ever sent. Two sourcing rules now exist for one view — the cost of not migrating the legacy owner.
- **Paging the archived list is now possible without another contract change.** Not built, and not needed today; the frame exists in a shape that can grow a cursor.
