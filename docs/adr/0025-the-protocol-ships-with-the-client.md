# The protocol ships with the client

`packages/shared` was created to hold the Panel↔Core wire contract, and [ADR 0016 D3](0016-the-0-1-0-shape.md) says exactly why: folding it into either side would make one image depend on the other and break the two-image split. That argument is still sound, and this ADR does not reverse it. What it settles is a question ADR 0016 D3 could not have asked, because there were only two clients and both were in this repository: **when a third party installs one package to talk to a Core, which package is it, and where is the frame schema they are typing against?**

[#129](https://github.com/actana/control/issues/129) answers "one package": `@actana/sdk`. The Panel's core-link client becomes that package by extraction, the CLI is built on it, and automations use it. So the frame schema has to be reachable from it. There are only two ways to arrange that, and they are not close: the SDK depends on `@actana/shared` and drags a private package into a published dependency graph, or **the protocol definition moves into the SDK and the SDK is where it lives.** This record takes the second. `core-link-frames.ts` moves out of `packages/shared` into `packages/sdk`, and everything that was importing it — the Core included — imports it from there.

The consequence worth stating up front, because it reads backwards: **the Core, which is the *server* answering these frames, now imports them from the *client* package.** That is deliberate, it is D2, and the alternative is a mirror.

## The decisions

**D1 — The protocol definition lives in the client package.** `packages/sdk/src/core-link-frames.ts` is the frame schema: every request, response, stream and event frame, the `CoreLinkEvent` envelope, `CORE_LINK_PROTOCOL_VERSION`, and the parse/serialize codec. `@actana/sdk` is the package a third party installs to speak to a Core, and the schema is the thing they are speaking. Shipping the two as one artifact is what makes "install the SDK and you have the protocol" true without a second install and without a version pair to keep in step.

**D2 — The Core imports its frames from the SDK, and this is not a layering violation.** A Core is the server; the SDK is the client. The arrow looks inverted and is not, because **what the Core depends on is the protocol, not the client.** The dependency is on one self-contained module with no I/O, no transport and no imports of its own — the same module it depended on yesterday, at a different path. A dependency graph is a claim about what breaks what, and nothing about the Core breaks when the SDK's transport changes; only a change to the frames touches it, and a change to the frames is by definition a change to the Core's own contract.

Stated as the rule a reviewer can apply: **`@actana/core` may import `@actana/sdk/core-link-frames` and nothing else from `@actana/sdk`.** The transport, the session layer and the durable entry that phase 1 adds are client machinery, and a Core that reached for them would be a Core dialling itself.

**D3 — There is exactly one definition of every frame type, and a mirror is never the answer.** This is the decision the other three exist to serve. The alternative to D2 is the Core keeping its own copy of the schema — hand-copied, structurally identical, and free to drift — and the project already knows what that costs: [#129](https://github.com/actana/control/issues/129)'s prototype CLI, which lives outside this repository, carries a hand-copied 90-line mirror of these frames, and it drifts silently the moment anything here moves, because nothing compiles the two against each other. A mirror does not fail; it disagrees, at runtime, on a wire, between two processes that each believe they are correct. Duplicating a schema to keep a dependency arrow pointing the conventional way trades a compile-time error for a production one.

**D4 — `packages/shared` stays private, and keeps everything that is not the protocol.** It is not deleted and it is not published. `core-mutations.ts`, `core-query.ts`, `event-log.ts`, `registration-blob.ts`, the harness helpers and the rest stay where they are, and the three modules typed against the frames now import them from `@actana/sdk` like every other consumer. ADR 0016 D3's argument survives intact — shared still exists so that neither image depends on the other — narrowed by one file. Its `description` is corrected to stop claiming the wire contract, because a manifest that describes a file it no longer contains is the next reader's wrong turn.

**D5 — `CORE_LINK_PROTOCOL_VERSION` does not move.** Not its value and not its meaning. This is a file move: the same constant, the same string, in a file that changed directories. A protocol version exists so that a Core and a client can refuse each other honestly, and nothing about where the definition is checked in changes what either of them speaks. Bumping it here would mark every Core in every fleet needs-update for a refactor no operator can observe — the same reasoning [ADR 0024 D11](0024-a-core-serves-many-clients-one-holds-a-sessions-write-lock.md) gives for a capability that does not move it. The packaging scripts that read the constant out of the source by regex are repointed at the new path and their unit test reads the real file, so a move that missed one of them fails the suite rather than shipping a stale version in every tarball.

**D6 — `packages/sdk` carries the train's version, and the cut writes it.** A workspace package with a `version` field that no cut writes and no check reads is a manifest that drifts. So the fifth manifest joins the four: [ADR 0023 D3](0023-release-trains-and-digest-promotion.md) is amended in this PR, `promote.yml`'s cut writes five, and `ci.yml`'s `Train rules` job asserts five. The check gained a guard while it was being extended, because the failure this ADR's own change could have introduced is not drift but a check that quietly covers less than the repository has: `Train rules` now asserts that its list covers **every** workspace package under `packages/` before it compares any versions, so the next package fails the check until it is added rather than being skipped by a loop that still reports green. The count in D3 is now derived rather than declared, and the number written in its prose will go stale again without becoming wrong about anything that matters.

**D7 — The SDK is not published to npm in this phase, and is `private: true` until it is.** [#148](https://github.com/actana/control/issues/148) says so and this record holds to it: nothing in phase 1 publishes, the package has no build and no `main`, and it is consumed through the workspace exactly as `@actana/shared` is. `private: true` is the honest encoding of that — a package that is not ready to publish and does not say so is one `pnpm publish` away from a version nobody meant to release. Removing the flag is a decision with a name and an owner, and it belongs to the ticket that publishes.

## Considered Options

- **Leave the frames in `packages/shared` and have `@actana/sdk` depend on it (rejected).** The smallest diff, and it keeps the dependency arrow pointing from client to shared to nothing. Rejected because it makes a *private* package a dependency of the one package this effort exists to publish. Either `@actana/shared` gets published too — which is the opposite of ADR 0016 D3's posture and drags the harness helpers, the registration blob and the query contracts into a public API surface nobody designed — or the SDK ships with a dependency that cannot be resolved outside this repository, which is not a package.
- **Move the frames into `packages/core` and have the SDK depend on the Core (rejected).** The conventional arrow: the server owns the protocol it answers. Rejected because it inverts the actual burden. `@actana/core` is a Node daemon with `better-sqlite3` and `node-pty` in its dependency closure, and a browser client that imported its frames from it would be importing from a package that cannot load in a browser at all. The frames file compiles under both the Vite and CommonJS tsconfigs precisely because it is self-contained; putting it inside the Core makes the light thing live inside the heavy one.
- **A fourth package, `@actana/protocol`, that both the SDK and the Core depend on (rejected).** The textbook answer, and it is genuinely defensible: the protocol is neither client nor server, so give it its own home. Rejected on the third-party story, which is the one this effort is for. It makes installing "the SDK" a two-package proposition with a version pair to keep aligned, and it adds a sixth manifest to the cut to solve a layering aesthetic. If the SDK ever grows enough surface that the frames are a minority of it, this is the option to revisit — and it is a cheap change from here, because D1 already put the frames in one file that imports nothing.
- **Duplicate the schema: the SDK gets a copy, the Core keeps its own (rejected, D3).** Every dependency arrow points the conventional way and nothing is shared. Rejected because the project has a working example of what it produces, in the prototype CLI outside this repository, and the failure mode is a wire disagreement between two processes that each typecheck cleanly.
- **Bump `CORE_LINK_PROTOCOL_VERSION` because the protocol's package changed (rejected, D5).** Superficially tidy. It would mark every Core in every fleet needs-update for a refactor no operator can observe, and it would make the version a fact about this repository's directory layout rather than about what two processes speak.

## Consequences

- **`@actana/core` depends on `@actana/sdk`.** New, deliberate, and bounded by D2's rule to the frames module alone. A reviewer who sees the Core import anything else from the SDK should treat it as a defect in this record's terms, not a judgement call.
- **`@actana/shared` depends on `@actana/sdk`.** `core-mutations`, `core-query` and `event-log` are typed against the frames and now reach them by package name. Shared is no longer the leaf of the graph, and its manifest no longer describes the wire contract.
- **The frames file is reached by package name from four places** — Core, Panel, shared, and the SDK's own test — and by relative path from none. Two Panel modules were importing it as `../../../shared/src/core-link-frames`; they now go through `@actana/sdk`, which is ADR 0016 D3's "make the boundary real" applied to the two files that had been getting away with it.
- **`tsconfig` paths, the Vite alias and three vitest aliases each gained one line.** The mapping is mechanical and duplicated by design: the same mapping stated in the type checker, the bundler and the test runner, because each of the three resolves independently and a missing one fails in only one of them.
- **The fifth manifest is now a promotion-blocking assertion** (D6). A train whose `packages/sdk/package.json` disagrees with the branch cannot merge anything.
- **The prototype CLI's mirror is untouched and is now further out of step.** **It does not live in this repository** — it is a file in #129's prototype CLI, outside this tree, and a sweep of every tracked file here at the time of writing finds no second copy of the frame schema. So there was nothing in this repository for #152 to repair or delete, and a reader of this record should not go looking for one. Freezing the mirror and deleting it is #129 phase 2's work, in the tree that holds it. It is named here so the next reader knows the drift is known and owned rather than missed.
- **A rename of this file now breaks four packages instead of one.** That is the point of the exercise and not a cost worth mitigating, but the packaging scripts are the exception: they read the constant out of the source text by regex because they are plain `.mjs`, so a move that missed them would ship a stale protocol version in every tarball. `scripts/__tests__/core-tarball.test.mjs` runs the parser against the real file for exactly this reason, and it is what caught the path in this change.
