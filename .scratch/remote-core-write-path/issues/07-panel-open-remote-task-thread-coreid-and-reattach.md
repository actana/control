# 07 — Panel: open a remote-Core task (thread `coreId` end-to-end + Core-aware revalidation + `sessionsList` reattach)

**What to build:** Issues 05/06 built the remote spawn transport (`electron/remote-core-dialer.ts`, `electron/core-pty-bridge.ts`, fleet IPC) and the creation UI. `TerminalPane`'s routing already picks loopback vs remote from `descriptor.coreId` (`src/components/views/TerminalPane.tsx:786-790`). But the upstream inputs — the terminal store and the code that constructs sessions — never got a `coreId` field, so every pane falls through to local `electron.pty` on the Panel's machine. Meanwhile, `TaskRowMini` (`src/components/views/FleetView.tsx:466`) is a plain non-clickable `<div>`, so a remote task can't even be opened. Close the loop: (a) add `coreId?: string | null` to `OpenTerminal` and thread it into `TerminalDescriptor` via `TerminalPanel`/`SessionGrid`; (b) make the startup revalidation Core-aware — a session with a remote `coreId` revalidates via `electron.fleet.tasksList` for that Core, not local `api.getTask`, otherwise every remote session is dropped on next launch; (c) turn `TaskRowMini` into a button that opens a session bound to `(coreId, task, project)`, using the Core's project `path` as `cwd`; (d) reattach on open by consulting the Core's `sessionsList` (the `setLivePtyProbe` wiring in `electron/harness-entry.ts:154` already reports live PTY ids) so reopening a task attaches instead of double-spawning. No protocol or Harness changes — the VM side is already ready.

**Blocked by:** 06 — needs the per-Core creation UI + `TerminalPane.coreId` routing already in place.

**Status:** ready-for-agent

**Symptom this fixes:** operator creates a task on a remote Core (Fleet view → New task, path `/root/Repos/<project>`). Harness DB records the row (`event_log` shows `task:created`), zero `pty.spawn.rejected` warnings, but no `pty:spawn` ever fires because the Panel never sends a `spawn` frame — `tasksMutate` reaches the Core, `spawn` doesn't. In the UI the task row is grey and non-interactive; on next Panel launch, if a session ever *does* land in the store with a remote `taskId`, revalidation 404s locally and `close()`s it.
